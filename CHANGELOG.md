### Lane V
- **The Nebius commands in `deploy/` are the documented ones** (W0, before the first GPU night; checked against the Nebius CLI reference pages auto generated on 19-Oct-2026, read Oct 21, 2026). `student_endpoint.sh stop` ran `nebius ai endpoint stop --name`, but `start` and `stop` take the endpoint's id (`--id`, required) and have no `--name`, so the stop the cost story depends on would have failed; `train_job.sh` ran `nebius ai create --type job`, the interactive wizard, where scripts use `nebius ai job create`.
  - `deploy/train_job.sh` runs `nebius ai job create` with `--platform`, `--preset`, `--volume <bucket>:/data`, `--disk-size 200Gi`, `--timeout 2h` (the job's own limit), `--container-command bash` and `--args`, plus `--subnet-id` (`RATCHET_SUBNET_ID`) and `--registry-secret` (`RATCHET_REGISTRY_SECRET`, a private image) only when set. `DRY_RUN=1` adds `--dry-run` and returns without waiting for the adapter.
  - `deploy/student_endpoint.sh` takes `create | start | stop | status`. `create` (once) is the old `start`; `start` (still the default) and `stop` run `nebius ai endpoint start|stop --id <id>` on the same endpoint, so its URL and token stay the same. The id is `RATCHET_ENDPOINT_ID`, or found by name in `nebius ai endpoint list --format json` (read with `RATCHET_PYTHON`, standard library only); `start` creates the endpoint when none has the name. The lookup never guesses: output that is not JSON, two endpoints with the name, an endpoint without an id, or a name missing from a list with more pages stops the script before anything starts, stops or is created (a second endpoint would bill a second GPU). `status` prints `<id> <state>`. `DRY_RUN=1` adds `--dry-run` to `create` and prints `start` and `stop` (which have no `--dry-run`) instead of running them; neither script accepts a `DRY_RUN` other than `0` or `1`, so `DRY_RUN=true` never starts a paid GPU. Each command is echoed with the token hidden; uptime is still recorded after `create`, `start` and `stop` (best effort, not in a dry run).
  - The endpoint's vLLM arguments add the model card's `--mamba_ssm_cache_dtype float32`, a context cap (`--max-model-len`, `RATCHET_SERVE_MAX_LEN`, default 8,192 instead of the card's 262,144), `--max-num-seqs` (`RATCHET_SERVE_MAX_SEQS`, 64), thinking off by default (`--default-chat-template-kwargs '{"enable_thinking":false}'`, vLLM v0.18.0; `RATCHET_SERVE_TEMPLATE_KWARGS`, checked as a JSON object before `create`, empty to leave it out) and, with `RATCHET_REASONING_PARSER_PLUGIN`, the card's `nano_v3` reasoning parser. The image is `RATCHET_VLLM_IMAGE` (default `vllm/vllm-openai:v0.18.0-cu130`; `v0.18.0` is the CUDA 12 build).
  - The scripts and docs no longer say a stopped endpoint costs nothing: it is not billed for compute or its own storage, but the mounted bucket still is (Nebius Serverless overview, read Oct 21, 2026). PRD §10 and Q5 say the same.
  - `config.DEPLOY_ENV` lists the 18 variables only the two scripts read; `KNOWN_ENV` includes them, so the traceability check holds each to a row in CONFIGURATION.md's deploy section. The package reads none of them, and nothing on the request path changed: the reference simulation, the three reference workloads and `/ratchet/stats` are unchanged.
  - 6 new tests (839 in total), all offline with a fake `nebius` first on `PATH` (`fakes.FakeNebius`, which prints the new `tests/fixtures/nebius_endpoint_list.json`) and a stub `ratchet.cost`: the job's exact `ai job create` call, start and stop by id, the lookup's refusals, the `create` flags and vLLM arguments, no "costs nothing", and `DEPLOY_ENV` against the scripts. `test_deploy_script_records_uptime_and_never_fails_on_it` (test_cost.py) uses the same fake. Docs: DEPLOYMENT (the four actions, the id lookup, `DRY_RUN=1`, the training command), DAY1 (checks 11 and 12: both scripts with `DRY_RUN=1` on Oct 22, the real list pasted into the fixture, vLLM starting with the arguments), CONFIGURATION, deploy/CLAUDE.md, RUNBOOK, README, TESTING, `docs/lanes/v-invariants.md` (one proposed invariant).

### Lane F
- **Verified savings receipts** (PRD FR-15.5 now Done, [ADR 0029](docs/adr/0029-verified-savings-receipts.md)). Ratchet is priced on savings, but a student answer's all-teacher baseline was the token formula's guess (300 reasoning tokens nobody measured) and the ledger is a file the vendor can edit. Now each ledger day gets a signed receipt for the gateway and one per API client, and billing reads only those.
  - New `ratchet/receipts.py`: each request becomes a leaf of metadata in whole nano-USD (`LEAF_KEYS`: no request text, the key's name only); per task, the ratio of audited teacher bills to the formula's estimates (`stats.ratio_estimate`, weights 1 / `label_p`) scales the served answers' baseline, with Cochran's variance (finite population correction, normal approximation); a task below `RATCHET_RECEIPT_MIN_AUDITS` (30) audits, or with answers logged before the estimate existed, is not billed, nor are stand-in answers (degraded, fallback teacher). The fee is `RATCHET_TAKE_RATE` (0.25) of the one-sided 95% lower bound of the billable savings, less the day's spend outside requests, rounded down; 0 with no calibrated task. The gateway-wide receipt also carries the day's GPU-hours view (informational).
  - The receipt (`ratchet.receipt/v1`) holds an RFC 9162 root over the day's leaves, the totals, the calibration and the bill, and the sha256 of the same client's previous receipt, signed with the BOM key; it is sealed once the day is over (5 minutes after it ends on a live ledger, whose days count from its first request) and written once (`Ledger.add_receipt`, `ReceiptExists`; INV-17's triggers). Sealing runs after each mock night, on `python -m ratchet.live seal` (hourly cron, RUNBOOK), lazily on any receipt endpoint and offline with `python -m ratchet.receipt seal --db`.
  - Every chat completion now carries its ledger row as `X-Ratchet-Request-Id` and `ratchet.request_id` (also in the last stream chunk; `ratchet.row_id` since the merge with lane E2, below). `GET /ratchet/receipts`, `/ratchet/receipts/{period}[?client=]`, `/ratchet/receipts/{period}/proof/{request_id}` (the leaf and its audit path against the signed root) and `/ratchet/receipts/{period}/leaves`: with keys on, an API key reads its own receipts only and an admin key every receipt; open in the mock demo, 403 in live mode without keys. Rows changed after sealing get a 500 and one `integrity` event, never a proof that fails.
  - `python -m ratchet.receipt verify r.json [--public-key K] [--prev p.json] [--proof x.json] [--rows leaves.jsonl]` checks the signature, the chain, a request's inclusion and, from the leaves, every total, estimate and the fee; it prints OK/FAIL lines and exits 0 or 1. `bom.verify` takes the schemas it accepts (`accepted=`) and treats a malformed signature as a failure instead of raising.
  - The mock teacher can bill reasoning that varies around a mean (`RATCHET_MOCK_TEACHER_REASONING_MEAN`; `python -m sim.simulate --receipts --teacher-reasoning-mean 420`, which prints each day's calibrated baseline and lower bound next to the true all-teacher cost, asked of the mock teacher in memory). With 420 tokens the receipts measure R of about 1.3 to 1.4 for `ticket-triage` and the bound held on every day of a 5-day run (simulation, mock models). Unset, every number is as before.
  - The three receipt settings are read and checked now (`Settings.receipt_policy()`, `checked_mock_reasoning_mean()`) instead of reserved; a bad value stops startup, because a sealed receipt can never be corrected.
  - Sealing reads the ledger and writes receipts only, with no model call or random draw, and the simulator seals only with `--receipts` (its results gain a `receipts` key only then): the reference simulation and the three reference workloads are unchanged, and `/ratchet/stats` is unchanged.
  - 41 new tests (833 in total): leaves without text, exact integer sums over 100,000 rows, the estimator's ratio and its bound's coverage on 200 seeded populations, weights and the finite population correction, unbilled tasks and stand-ins, the fee, sealing once with no write on a second call, from 8 threads and two connections, days read in chunks with the lock free, signatures and chains broken by edits, per-client receipts, `recheck`, verifiers that never raise, the request id and its proof over HTTP, key scoping, rows changed after sealing, bad settings, the mock teacher's reasoning, the simulator moving no number with sealing on and measuring R > 1.2 at 420 tokens, and both CLIs.
- **Verified savings receipts: review fixes** (FR-15.5, ADR 0029).
  - `verify_chain` and `verify_proof` raised `AttributeError` on a receipt (or a previous receipt) whose `period` was a string, a number or a list, and `python -m ratchet.receipt verify --prev/--proof` printed a traceback instead of exiting 1. The verifiers now read `period.day` through a checked helper (`receipts._day`) and catch any other exception as a FAIL line, as `verify_receipt` and `verify_rows` already did; `recheck` uses the same helper. A seeded run of 2,000 nested mutations raised 72 times before and none after.
  - Stand-in answers (`degraded`, `fallback_teacher`) stay outside the billable set, but what they lost now counts: `savings.stand_in_loss_nusd` = Σ min(0, baseline − cost) over them is added to the billable savings. A fallback teacher's answer after the student answered loses about the student's cost when the two teachers are priced alike; leaving it out raised the fee. A stand-in's gain is never billed. With the fallback teacher and degraded mode off (the defaults) the term is 0.
  - `RATCHET_MOCK_TEACHER_REASONING_MEAN` out of range now stops startup in live mode too (the gateway and `python -m ratchet.live`), as CONFIGURATION.md says; it was checked in mock mode only.
  - Docs: a ledger day starts at the first request's time of day, not at 00:00 UTC, so the RUNBOOK, DEPLOYMENT and cloud-init cron lines run `python -m ratchet.live seal` hourly (a run with nothing due writes nothing); ADR 0029's Limits and the threat model (new T25) say that request ids are the ledger's global row ids, so a client can infer the gateway's total volume between two of its requests.

- **Ledger time machine** (PRD FR-16.5 now Done, [ADR 0028](docs/adr/0028-designed-propensity-replay.md)). Ratchet designs its own labelling (an escalated request is labelled by the teacher with probability 1, a served answer with the audit rate it was drawn at), so every label's probability is known; audits alone cannot say anything about thresholds below the live one, and the baseline's 300-reasoning-token assumption was never measured.
  - The request path only logs, on every row where the student answered: `threshold` (the value the answer was compared with), `label_p` (as since ADR 0025), `student_agree` (`task.agree` of the student's answer and the primary teacher's valid answer from the escalation or a random audit; equal to `audit_agree` on audited rows; never from a shadow arbitration, the fallback teacher, a degraded answer or an invalid answer) and `baseline_est_usd` (the token formula, new `Ratchet._formula_baseline`, for every student answer; a served answer's `baseline_cost_usd` is that same value to the bit). At most one `task.agree` and one `Task.check` per escalation, no model call, no random draw, no extra SQL statement. No `reason` column: `route` already says it (ADR 0024).
  - New `ratchet/replay.py`: `load` (one version's rows from the new `Ledger.replay_rows`, with the rows left out counted: `before_logging`, `no_student_answer`, `pinned_now`, `malformed`), `at` (exact coverage; Hajek precision weighted by 1 / `label_p` with an approximate interval, Wilson at Kish's n_eff; null with the reason "audit rate was 0: precision above the live threshold cannot be identified" without positivity; cost = student spend + unserved all-teacher cost + audit rate × served all-teacher cost, savings and errors per 1,000; with no threshold, each request at the threshold it was logged with), `sweep` and `frontier` (0.30 to 1.00 every 0.01 in one sorted pass, each row equal to `at`), `ratio` (the calibrated baseline: Cochran's ratio estimator on audited served answers, `insufficient` below 30), `suggest` (a fixed-sequence scan of `CERT_GRID`, always marked "approximate interval, not a certificate; thresholds change only through Night School"; the original proposal's "Learn-then-Test" was not one, so nothing applies it) and `money_left_on_table`. `stats.wilson` takes a fractional n.
  - `GET /ratchet/replay?version=&threshold=&audit_rate=&since_day=&until_day=` (what happened next to the counterfactual, the calibrated baseline) and `GET /ratchet/replay/frontier?version=&target=` (the frontier, the advisory suggestion, the money left on the table): read-only and public like `/ratchet/stats`, both modes, the live version by default (400 without one), one version only (`version` twice, a list or a word is a 400: confidence scales differ between versions), labelled `simulation (mock models)` in mock mode and `per_token`.
  - `python -m ratchet.replay --db PATH [--version V] [--sweep 0.3:0.95:0.05] [--audit-rate A] [--target 0.97] [--since-day D] [--until-day D] [--json]` prints one table per version (labelled as simulation when the simulator wrote the ledger); `python -m sim.simulate --db PATH` keeps a run's ledger in a new file (never an existing one, never with `--compare-release`).
  - In the seed-7 bad-deploy run (6 days of 1,500 requests; simulation, mock models) the live v1 replays 6,208 requests at 97.7% coverage and 99.2% precision (approximate 95% interval 98.1% to 99.7%) at its threshold 0.5, and at 100% coverage and 97.0% precision at 0.30; the corrupted v3's 123 requests replay at 40% precision. R is 1.000 there because the mock teacher writes exactly the assumed reasoning tokens.
  - Logging only, with no random draw: the reference simulation and the three reference workloads are unchanged. `/ratchet/stats` is unchanged.
  - 15 new tests (788 in total): the Hajek estimate and cost on a hand-computed example, exact coverage and the frontier, positivity, unbiasedness by seeded Monte Carlo (and a `slow` full-size run), the suggestion and the money left on the table, the ratio estimator recovering 1.3 (`test_core.py`); each version's logged coverage and audited precision reproduced over the bad-deploy run, `label_p` and `student_agree` following the design, the endpoints on the mock gateway (`test_system.py`); the columns on 17 paths with no extra call (`test_contract.py`); an old file migrating with its rows counted, malformed rows, mixing versions refused, pinned tasks (`test_hardening.py`); `--db` and the CLI (`test_live.py`). Docs: ADR 0028, API (Ledger replay), ARCHITECTURE §1, §2, §4 and §7 (calibrated baseline and the replay), RUNBOOK (reading the replay frontier), README, GLOSSARY, THREAT_MODEL (T1), `docs/lanes/f-invariants.md` (one proposed invariant).
- **Ledger time machine: review fixes** (FR-16.5, ADR 0028).
  - An escalation now labels the student (`student_agree`) only when the teacher answered it under an audit's conditions: one choice, and the serving parameters equal to the audit's once the client's `logprobs` and `top_logprobs` are set aside (`router._labels_like_audit`). Before, an escalation under a client's temperature, seed, `logit_bias` or penalties, or for n > 1 choices (sampled at 0.7), compared the student with a sampled or client-steered teacher answer below the threshold while audits compared it with the deterministic answer above it: two estimands in one weighted mean, and a `logit_bias` client could choose the labels (threat model T2). Such an escalation now leaves `student_agree` NULL, a designed label not obtained.
  - `GET /ratchet/replay?version=²` (or `①`, `1²`, and the frontier) was a 500: `str.isdigit()` accepts those digits and `int()` refuses them. Now a 400.
  - The replay's current threshold is the one the router uses: the configured default for the hosted fallback student in live mode without a student endpoint, not the version's. Rows logged at `SERVE_NOTHING` while their task's spec is still changed for the version are never served at any replayed threshold (`Row.spec_changed`); they were counted as servable.
  - The gateway runs one replay at a time (another request meanwhile is a 429 with `Retry-After: 1`), and `Ledger.replay_rows` reads in chunks of 20,000 rows on a new index (`requests_version_id`, on `student_version, id`, in `INDEXES`), each under the ledger lock, up to the last request id when it began, so `log_request` no longer waits for a whole history: for a version of 400,000 rows the longest hold went from 2.8 s (one read) to 0.25 s, the whole read from 2.8 s to 3.4 s (one laptop-class run, synthetic rows).
  - Docs: API.md says what `actual` counts (the threshold decision as logged: a degraded answer is not served, audits at their expected cost, arbitration spend left out) and that an n > 1 request that escalated below the threshold with a split vote is counted as servable (no column records it); ADR 0028 and `docs/lanes/f-invariants.md` state the one-teacher rule; the FR-16.5 traceability entry no longer names `stats.hajek_mean`, which the replay does not call (it keeps running sums so a frontier is one pass).
  - Logging only: the reference simulation and the three reference workloads are unchanged (the simulator sends no client parameters and one choice). 4 new tests (792 in total) and 7 new contract paths (24).
- **Committed training sets** (PRD FR-16.4 now Done, [ADR 0027](docs/adr/0027-committed-training-sets.md)). A v1 BOM's `dataset_sha256` hashes the concatenated example hashes: nobody can check one example against it without the whole list, it cannot show that an example is absent, and it binds no label, teacher or license. Invariants 3 and 6 (golden rows never trained on; precision measured on held-out rows) were claims an auditor could not check.
  - Every night now commits to the exact rows it hands the trainer and the golden eval: a `merkle.KeySet` (collapsed sparse Merkle tree, ADR 0024) per split, keyed by the example hash and valued by `dataset.leaf_value` (SHA-256 of the canonical `{completion, teacher, license, redactions}`). `run_night` builds both before the training job (a duplicate key stops the night before any GPU time), writes the leaves once right after `create_version` (`Ledger.set_version_leaves`, refused for a split that already has leaves, an unknown version or malformed hex; append-only by trigger, INV-17), and signs root and size in the v2 BOM (`training.commitment`, `golden.commitment`). A failed training job writes no version and no leaves. `Ledger.version_leaves`, `versions_containing(key)` (the versions trained on an example) and `bom.commitment(m, split)` read them back.
  - `POST /ratchet/versions/{id}/proof?split=train|golden` (admin key): by `{"key"}` or by the chat request itself, validated, normalised and redacted exactly as the gateway stores it (`proof.resolve_key`; a request with a teacher-only part is a 400, because it is never stored), a membership or non-membership proof against the signed root, with the leaf value when included. `GET /ratchet/versions/{id}/heldout` (admin key): the golden leaves and every golden key's proof of absence from the training root (about 113 KB for 133 golden rows against 1,288 training leaves, mock demo after four simulated days). 404 `commitment not available` for a version trained before v0.5. The gateway caches the last 8 trees per runtime and only ones that rebuild the signed root and size; leaves edited outside Ratchet get a 500 and one `integrity` event (new kind), never a proof. Mock-only `GET /ratchet/demo/sample-example` returns a committed example's prompt (never its answer) as a body for the proof endpoint.
  - `python -m ratchet.proof verify proof.json --bom bom.json [--public-key K] [--expect included|absent]` and `heldout cert.json --bom bom.json` check proofs and certificates offline against the root the BOM signs (never the file's own root, result or value), with the BOM's signature; `key --task T --messages m.json [--no-redact]` prints the key a request is stored under. Exit 0, 1 on any failed check, 2 on bad input. Non-membership is sound even against the operator who built the tree; a sorted-list tree would not be (ADR 0027). A proof shows the operator's signed commitment at training time, not that the weights came from that dataset.
  - Live mode: `python -m ratchet.live night` writes the BOM into the adapter's folder too (`adapters/<name>/ratchet_bom.json`; a name that is not one folder is skipped) and runs `RATCHET_SYNC_CMD` again; a failed upload makes the command exit non-zero after the night's report. Closes the roadmap item "BOM copy inside the adapter folder".
  - The proof endpoints use the existing admin keys (`RATCHET_ADMIN_KEYS`) instead of a new client list: with guessable texts they are a membership oracle for the training data (threat model T23). No new setting.
  - Night-time only, no random draw and no request-path change: the reference simulation and the three reference workloads are unchanged.
  - 14 new tests (773 in total): leaf values, `version_leaves` written once, two nights committing exactly their rows, a failed job committing nothing, the request key equal to the stored hash (redaction on and off), the endpoints and the CLI on a signed mock gateway, an edited leaf caught against the signed root, v1 BOMs, verifiers that never raise on malformed files (a regression: a non-list `siblings` raised `TypeError`), admin keys in live mode, the CLI's `key` (`test_provenance.py`); every version's golden keys proved absent from its signed training root over the six-day bad-deploy run (`test_system.py`, INV-3); BOM copies never written outside the data folder and the live night's second sync (`test_live.py`); the sample endpoint refused in live mode (`test_contract.py`). - **Retries neither pay twice nor drain the golden set** (PRD FR-1.70 new, INV-3 extended, [ADR 0071](docs/adr/0071-idempotency-keys-and-retry-de-duplication.md); ADR 0007 amended). - **`Idempotency-Key`** (new, `ratchet/idem.py`): 1 to 255 printable ASCII characters (else a 400 `invalid_idempotency_key`), per API key (by its name, never the key). The first request with a key runs the cascade and a 200 answer is kept in memory, never on disk (INV-12), for `RATCHET_IDEMPOTENCY_TTL_S` (new, 600 s; up to `RATCHET_IDEMPOTENCY_CACHE`, new, 10,000 answers and 64 MiB, least recently used dropped first). The same key and body while it runs waits for it (at most `RATCHET_TEACHER_DEADLINE_S`, and at most four waiters per key, since a waiter holds a worker thread and uses no quota; past either, a 409 `idempotency_key_in_use` with `Retry-After: 1`, which the SDKs retry) and gets its answer; afterwards the same body (the same completion id, or the same stream events) comes back with `Idempotent-Replayed: true`, with no cascade, ledger row, quota use or rate-limit headers. The same key with another body (sorted-key JSON plus `X-Ratchet-Task`) is a 400 `idempotency_key_reused` with `X-Should-Retry: false`, not a 409, which SDKs retry. An error is never kept: a failed first request releases its key, so the retry runs again.
