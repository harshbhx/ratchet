# ADR 0043: Tool calls: teacher-only by default, opt-in distillation later

- Status: Accepted
- Date: 2026-10-21

## Context

Before this decision a request's `tools` reached no model by default ([ADR 0017](0017-generation-parameters-by-role.md)): the provider read only `message.content`, the response had no `message.tool_calls`, and a teacher answer that was a tool call was refused (502 `tool_calls_unsupported`). So:

- An agent framework (the OpenAI SDK's tool loop, LangChain, LlamaIndex) could not use the gateway at all: it got prose where it expected calls.
- Worse, the prose was distilled. The teacher answered a prompt stripped of its tools, and that answer was stored as the training target for a request that asked for a call: the student learned the wrong kind of answer, and served it once confident.
- A conversation that already carried tool calls and tool results (the second turn of a tool loop, sent without `tools` again) went through the cascade like any other request.
- The legacy `functions` and `function_call` fields were checked but not mapped.

Distilling tool calls needs more than forwarding the tools: the student's vLLM runs without a tool parser, a stored call needs comparators of its own (which tool, which arguments), and its redaction and its golden eval need rules. That is a separate item (tool-call distillation). This decision makes tool calling work end to end now, without training on any of it.

## Decision

- **What a tool request is** (`openai_compat.uses_tools`, `router.uses_tools`): non-empty `tools` or `functions`, or a message with `tool_calls` or `function_call`, or a message whose role is `tool` or `function`. `tool_choice: "none"` with tools is still one: the teacher is told not to call, but the conversation is a tool exchange. An empty `tools` list, or `tool_choice` with nothing to call, is not one (those fields are then not sent).
- **The teacher answers it alone, and nothing is stored** (`Ratchet.handle` → `_teacher_only`, route `tools`). No student call, no audit, no shadow, no `add_example` (invariants 2 and 10 hold: the only stored answers stay teacher answers to the request as sent, and a request never pins a task). A pinned task and an unregistered task under `RATCHET_UNKNOWN_TASKS=teacher` keep their own route, since the operator's reason comes first; the row records `uses_tools` either way. The fallback teacher may answer when the primary is unavailable (route `fallback_teacher`), never stored; a teacher failure is mapped as on any teacher path (invariant 7). A task's `tools: distill` is honoured only once tool-call distillation is built; until then it is teacher-only too, because the cascade would answer without the tools.
- **The teacher gets the tool fields by default.** `tools`, `tool_choice` and `parallel_tool_calls` join the default `RATCHET_TEACHER_PARAMS` (`providers.DEFAULT_TEACHER_PARAMS` is every standard field). Only a tool request carries them, and only the teacher answers it, so no other path changes. The student never gets tools (`DEFAULT_STUDENT_PARAMS` is unchanged), and an operator who keeps tools from the teacher gets its prose answer, still teacher-only and not stored. The model sent is always the configured teacher (invariant 1); the client's `model` changes nothing.
- **The provider reads tool calls** (`providers._tool_calls`) into `Completion.tool_calls`, each exactly `{id, type: "function", function: {name, arguments}}`: the upstream id kept (vLLM's `chatcmpl-tool-…`, OpenAI's `call_…`), a missing or empty one replaced by `call_` and 24 random hex digits, a missing `type` taken as `function`, `arguments` always a string (an object or array from a lax server is JSON-encoded, a missing one is `{}`), vLLM's `index` and vendor keys dropped. A legacy `message.function_call` from an older server becomes one call. A call a client could not use (not an object, another type than `function`, no function name, text with an unpaired surrogate) makes the whole response a 502 `bad_upstream_response` (the client gets `teacher_unavailable`): serving the other calls would hand the client part of the model's answer. `text` is the content, `''` when there is none.
- **The response carries them as OpenAI does** (`gateway._message`): `message.tool_calls` with the ids as the teacher made them, `content` null (or the text the model wrote beside the calls), and `finish_reason: "tool_calls"`. `router._client_finish` sends `tool_calls` only for a choice that has calls (a server that ends calls with `stop` is reported as `tool_calls`; one that claims `tool_calls` without any is reported as `stop`), and keeps `length` and `content_filter`, since the arguments may then be cut short.
- **Streaming** (`gateway._call_deltas`): the role chunk (its `content` null when the choice is only calls), the content chunks if there is text, then one delta per call, `{"tool_calls": [{"index": i, "id", "type": "function", "function": {"name", "arguments"}}]}` with the whole arguments string, then the finish chunk. The answer is complete before the first chunk anyway (the cascade must see it), so there is nothing to gain from splitting the arguments, and this is what the OpenAI SDK's `ChatCompletionStreamState` and LangChain's chunk accumulators merge by `index`.
- **The legacy fields are mapped** (`openai_compat.tool_params`, `legacy_history`). Each of `functions` becomes `{type: "function", function: f}` after the request's own `tools` (a name `tools` already has is left out), and `function_call` becomes the `tool_choice` when none was sent. A legacy history goes to the teacher as tool turns, because most open-model chat templates know no `function` role: an assistant `function_call` becomes one `tool_calls` entry with a stable id (sha256 of its position and name, so a repeated request reads the same), and the `function` message that answers it a `tool` message with that `tool_call_id`. A request that used only the legacy fields gets the legacy form back: `message.function_call` (the first call's name and arguments) and `finish_reason: "function_call"`, streamed as one `function_call` delta. A legacy message holds one call, so such a request asks the teacher for one (`parallel_tool_calls: false` unless the request set it); if the teacher makes more anyway, the first is returned.
- **A `response_format` does not apply to a tool call.** It constrains the final answer's content. A tool call is never repaired ([ADR 0042](0042-auto-tasks-from-response-format-schemas.md)) and is left out of `schema_valid`, which is null when every choice is a call; a prose answer to a tool request is still checked.
- **A request without tools still refuses a tool call** (`Ratchet._ask_teacher`, which accepts calls only when `_teacher_only` serves a tool request): a teacher that answers such a request with a call, or with `finish_reason: "tool_calls"`, is a 502 `tool_calls_unsupported` with `X-Should-Retry: false`, on the cascade and on the teacher-only path alike (a pinned task, an unknown task, a multimodal request that offers no tools); an audit or arbitration counts it as a failed optional call. That answer could be neither compared, stored nor served as the answer to that request, and a client that offered no tools cannot run one.
- **A part only the teacher reads takes the same path.** A request with a content part listed in `RATCHET_TEACHER_MODALITIES` goes to `Ratchet.teacher_only` with route `multimodal` (before: `pinned`), so the two teacher-only reasons can be told apart in `/ratchet/stats`. No image bytes reach the ledger: `requests` holds metadata only, and nothing is stored as an example.
- **What is recorded.** `requests.uses_tools` (1 for a tool request on whatever route, 0 on the cascade, NULL in older rows; in `SCHEMA` and `MIGRATIONS`), `tool_requests` per task in `/ratchet/stats` (a new key; the keys only grow), and the usage estimate counts a call's JSON when the teacher reports no completion tokens.
- **Redaction is ready.** `redact.redact_messages` already redacts tool and function call arguments and tool results (string or text parts); a test pins that, because tool-call distillation will store tool turns and invariant 12 must hold the day it does.

## Alternatives considered

- **Keep stripping the tools and distil the prose.** Rejected: the stored target answers a different request than the one the client sent, and the student would serve prose to an agent loop that needs a call.
- **Let the student answer tool requests in prose and escalate the rest.** Rejected: the student is never sent tools, so even a confident answer is the wrong kind of answer.
- **Distil tool calls now.** Deferred to its own item: it needs a student endpoint with a tool parser, comparators for calls (tool name, arguments by field), a golden eval over them and storage rules for tool turns. Keeping tool requests out of the training set until then means no data has to be cleaned up later.
- **Split the arguments over several stream deltas, as OpenAI does.** No gain: the answer is complete before the first chunk, and every accumulator handles one delta per call.

## Consequences

- Agent frameworks and the OpenAI SDK's tool loop work against the gateway, streamed or not, in the current and the legacy form, in mock mode (the generic world's deterministic tool calls) and live.
- Tool traffic costs the full teacher price: no savings until tool-call distillation, and `tool_requests` per task shows how much of the traffic that is. The mock `tools` workload is now answered by the teacher alone and never trains the student (simulation).
- A conversation that carries tool turns is teacher-only even when it asks for a plain summary at the end: the student was never trained on such conversations, so serving it would be a guess.
- Examples stored before this change are untouched. None of them is a tool call, because the provider did not read calls before, but some may be prose answers to tool requests whose tools were stripped; they were stored without `tools` in their conditions (the teacher was not sent them), so they cannot be told apart from other rows. No live ledger has served tool traffic yet; one that did before v0.5 should start fresh or erase those rows before its next night.
- Proposed invariant (lane C): tool-call and multimodal requests are teacher-only and never stored unless their task opts in, and the client's `model` never changes that.
- The offline tool-calling exams in `evidence/toolcall` train an adapter outside the gateway; the gateway still does not distill tool calls.
