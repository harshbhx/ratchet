# ADR 0120: Judge access and a persistent Scout guard

- Status: Accepted
- Date: 2026-10-21

## Context

PRD §8.2 sets the project's own Stage One target: the hosted demo runs in live mode during judging (Dec 1–15, 2026) and makes runtime Token Factory and Tavily calls. The Best Use of Tavily prize needs a working runtime Tavily call. The VM guide tells operators to protect `/v1/*` before going live, so Scout is the only public path that makes those calls.

What the rules say comes only from web-search snippets of the rules page, which returns 403 to fetches (Oct 20, 2026), so it is **unverified**: judges are not required to test the project and may judge on the text, images and video alone; entrants must give access to a working project, and a private site must include login credentials in its testing instructions. A judge may never open the demo, but when one does, it has to work.

Five ways a judge could fail to get a live Scout run before this change:

1. **The public uses up the shared allowance first.** The Devpost gallery is public. Any visitor could spend the day's runs (`RATCHET_SCOUT_MAX_RUNS_PER_DAY`) and the daily USD cap before a judge arrived.
2. **The guard's counters lived only in memory.** `Runtime.reset` built a new `Guard`, so every `update.sh` run (`docker compose up -d --build`), crash restart or recreate reset them to zero. On a day with a restart, spend could pass the cap INV-11 promises.
3. **Tavily credits run out mid-month.** The free plan gives 1,000 credits a month; a basic search costs 1 credit and an advanced one 2; pay-as-you-go is $0.008 a credit ([Tavily API credits](https://docs.tavily.com/documentation/api-credits), checked Oct 20, 2026). The page does not say when the monthly credits reset. Scout makes up to 3 searches a run, so 30 runs a day is up to 90 credits a day, which lasts about 11 days.
4. **A search failure ended the run.** `Scout.run` called the search with no `try`. The planner's Token Factory call had already been made, but the run returned an `error` event and HTTP 502, and the writer never ran. Exhausted credits failed the same way: Tavily documents 432 "Key limit or Plan Limit exceeded" and 433 "PayGo limit exceeded" ([search reference](https://docs.tavily.com/documentation/api-reference/endpoint/search), checked Oct 20, 2026). (An earlier gap note said such a run "makes no Token Factory call at all"; that is wrong, the planner calls the teacher before any search.)
5. **A second gateway process doubles the budgets.** A second process on the same ledger file has its own in-memory guard. ADR 0006 and the compose file pin `--workers 1`, but nothing detects a second process.

Logs constrain how an access code may travel. uvicorn's access log writes the path with its query string, and Caddy's access log records the request URI and request headers, redacting only Cookie, Set-Cookie, Authorization and Proxy-Authorization by default ([Caddy log directive](https://caddyserver.com/docs/caddyfile/directives/log), [global options, `log_credentials`](https://caddyserver.com/docs/caddyfile/options), both checked Oct 20, 2026). The same check showed that guarded mode's `X-Ratchet-Admin-Token` was written in clear to Caddy's log.

## Decision

- **Spend rows with `usd` 0.** The `spend` table (ADR 0024) gets two kinds and no new column. `scout_run`: one row per admitted run, `ref` the run id, `detail` `{"judge", "llm_usd", "status"}` (`admitted`, then `done`, `error` or `search_unavailable`), updated after each model call so a process killed mid-run still counts what it spent. `tavily`: one row per search call, `detail` `{"judge", "credits", "depth", "http", "counted"}`. `usd` stays 0 for both: Scout's model calls are already in `requests.cost_usd`, and the savings receipts subtract `spend.usd`, so nothing is counted twice. Only `scout_run` rows may be updated (`Ledger.update_spend_detail`, `MUTABLE_SPEND_KINDS`). No row holds an IP, the question, a URL, an error message or the code. An index on `(kind, ts)` serves the restore.
- **Restore at startup, share nothing live.** In live mode `Runtime.reset` builds the guard with the ledger and calls `Guard.restore()`, which rebuilds today's runs, spend and largest finished run per pool from the `scout_run` rows since 00:00 UTC; the credit meter restores its cycle the same way. Restoring reads spend rows only, never `requests`, so retention jobs that fold request rows and `/v1` traffic that names Scout's tasks cannot move it. A run counts against the UTC day it was admitted on, in memory and after a restart. Per-IP windows stay in memory: no IP is stored.
- **A pool rule with a USD margin.** With the day's total T, the judges' reserve J, public use P and judge use U today, for runs and for USD: a public run is admitted only while P + max(0, U − J) + m < T − J, and a judge run only while P + U < T. For runs m is 0. For USD, m is the largest finished run today when a judge budget is reserved (0 otherwise, which keeps the v0.2 rule exactly), so public runs already in flight cannot spill into the judges' share. Judges get at least their reserve and can use public room that is left; runs stay at or under T exactly. Judge runs have their own per-IP hourly window, so public use from a shared address cannot use up a judge's hour. Refusals never hint that a code exists.
- **The code in a POST body once, then a signed cookie.** `POST /scout/judge` takes `{"code": ...}`, parsed by hand so no validation error can echo it, compares SHA-256 digests in constant time (as `KeyRing.identify` compares keys) and allows 10 attempts per IP per rolling hour. The gateway keeps only the digest and a cookie key, HMAC-SHA256 of a fixed context keyed by the code; the cookie is `v1.<expires>.<nonce>.<signature>`, `HttpOnly`, `SameSite=Strict`, `Path=/scout`, `Secure` in live mode. Sessions survive a restart because the key comes from the code, and rotating the code revokes them all. `SameSite=Strict` matters because `/scout/stream` is a GET that starts a paid run: without it another site could open a cross-site EventSource with a judge's cookie. Only the cookie makes a run a judge run; a code in a URL or body is ignored. `Settings.scout_policy()` checks the settings at startup (the code is 16 to 256 printable ASCII characters with no spaces, set if and only if judge runs are above 0, and so on) and no message prints the code.
- **Credits paced until a date, never refusing a run.** `CreditMeter` counts credits per cycle (starting at 00:00 UTC on `RATCHET_TAVILY_CYCLE_DAY`), reserves a search's table amount before the call and settles it after: `usage.credits` when Tavily reports it (the request sends `include_usage`; a value outside 0 to 10 is not believed), else the table; 0 for a 4xx (432 and 433 included) or a request never sent; the table amount for a 5xx or a failure after sending, because whether Tavily bills those is undocumented. A 432 or 433 pauses searching for an hour. With C the monthly credits, Cj the judge reserve and Q the public pool's use (public use plus judge use past the reserve), today's public allowance is (C − Cj − Q at 00:00 UTC) divided by the days left until `RATCHET_TAVILY_PACE_UNTIL` (while it falls in the cycle and is today or later) or the cycle's end, rounded down; unused credits roll forward. Judges draw on their reserve first, then on today's allowance, so public and judge use never pass C. When a search may not run, the run still runs without it: a judge who arrives without the code is a public visitor, and a run without search still gives them a Token Factory call, where a 429 would give them nothing.
- **Search unavailable is a labelled path, not an error.** `Scout.run` catches `SearchUnavailable` (a fixed reason) and `httpx.HTTPError` (named by class and status, never message or URL, as ADR 0013 names failed optional calls) around each search, emits the searcher step with `detail.unavailable`, stops searching, runs triage and reader on what was found, and calls the writer with what is left (an empty fact list when nothing was found; the writer's prompt and the mock teacher already handle it, so `prompts.py`, shared with the simulator, is unchanged). The writer step gains `detail.search_unavailable` and the `done` event `search: {available, partial, reason}`. `/scout/run` answers 200 for such a run. To keep a broken key visible, failures (not credit refusals) are counted in `/scout/status.search` and written as a `search_error` event on the 1st, 10th, 100th and 1000th, and the 503 for a missing `TAVILY_API_KEY` stays.
- **The single-writer lease is taken in the lifespan and defaults to `warn` (NFR-60, deferred).** When lane D's `leases` table lands, a `gateway` lease with a heartbeat will be taken in a FastAPI lifespan, never in `Runtime.reset` (tests build runtimes freely), in live mode only. `warn` writes a `gateway_lease` event and keeps serving, `exclusive` refuses to start, `off` does nothing. Until then `RATCHET_GATEWAY_LEASE` is a reserved setting: any value but `warn` stops startup.
- **Caddy's log drops the edge token.** The Caddyfile's `log` block uses `format filter` with `request>headers>X-Ratchet-Admin-Token delete`, wrapping the console format.

## Consequences

- The daily USD total can still pass the budget by the runs in flight when it is reached, as before; the run total cannot pass its cap.
- Credits are counted conservatively: a 5xx or a read timeout is charged at the table amount. The meter should read at or above the Tavily dashboard; the runbook says to reconcile weekly.
- A judges-only day is possible (judge runs equal to the run cap): the public then gets 429. It is allowed and documented.
- Per-IP windows reset on restart, as before; only the daily totals persist.
- The first restart after upgrading misses the runs from earlier that day (they have no rows), once.
- Restoring happens once, at startup. Two processes on one ledger still each enforce their own in-memory caps until NFR-60 detects the second one.
- The Scout page has an "I am a judge" control (`web/src/pages/scout/judge-code.tsx`) that opens a session with `POST /scout/judge`; it shows only when `/scout/status` reports `judge.enabled`. Judges without the code get the public pool.

## Alternatives considered

- **The ledger as the source of truth at every admission.** Reading the day's rows on each admit would also share the caps across processes, but it puts a query and a write on every admission and still races without a transaction across processes. Left to a later item for shared state across workers; restoring at startup covers restarts, which is what happens on the demo VM.
- **The code in a query string or a custom header.** Both are written to uvicorn's or Caddy's access log. A cookie is redacted by Caddy by default and never needs the code again.
- **Refusing public runs when credits are used up.** It saves two teacher calls per run, but a judge who did not get the code would get nothing. The run and USD caps already bound the cost.
- **Refusing to start when another process holds the lease, by default.** After a crash the dead holder's lease lasts up to its TTL, so a refusal by default could keep the demo down; compose already pins one worker.
- **Scout spend in `spend.usd`.** The receipts subtract `spend.usd` from the billable bound and a cost view may sum it, so Scout's model calls, already in `requests.cost_usd`, would be counted twice.
