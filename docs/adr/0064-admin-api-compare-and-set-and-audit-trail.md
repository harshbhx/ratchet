# ADR 0064: Admin API, compare-and-set transitions, audit trail

- Status: Accepted
- Date: 2026-10-21

## Context

The runbook's manual interventions were a Python REPL and raw SQL: `led.set_version(7, "rolled_back", 0)` and an `INSERT INTO events`. Nothing recorded who changed what or why, nothing checked that a move made sense (two live versions were one typo away), the SQL left `stage_since` alone, and there was no way to stop the student, hold releases, pause training, change the audit rate or keep one task on the teacher without editing the environment and restarting.

The release gate read a version and then wrote it with `set_version`, an unconditional `UPDATE`. In live mode two processes run the gate on one ledger file: the gateway's per-request `rt.tick()` and the cron `python -m ratchet.live tick`. Both can read a canary that is ready, and both promote it: two `canary` or `live` events, a stage restarted twice, and in the worst order a version promoted over one that was just promoted. An admin acting by hand would race the same way.

## Decision

- **Compare-and-set moves.** `Ledger.transition(vid, from_state, from_pct, to_state, to_pct, event)` runs `UPDATE versions SET state=?, traffic_pct=?, stage_since=(SELECT COALESCE(MAX(id), 0) FROM requests) WHERE id=? AND state=? AND COALESCE(traffic_pct, 0)=?` inside `BEGIN IMMEDIATE` and writes `event` in the same transaction only when one row changed; it returns whether it did. A move into shadow or canary is refused (False) while another version is in either, so at most one version is in flight. A move to live raises: `Ledger.promote_live(vid, from_state, from_pct, event, old_live=, retired_event=)` makes the version live and retires the live version the caller saw, both compared (the versions live now must be exactly `old_live`), in one transaction, with the retirement's event before the promotion's. So two versions are never live, and of two processes making the same decision, the second changes nothing and writes nothing.
- **The release gate uses them only.** `ReleaseGate.admit` runs in one transaction: it reads the version, acts only on a `candidate` (one an admin moved while it was scored is left alone, with a `conflict` event), retires an older shadow or canary and places the candidate, all committed together. The tick's steps keep their reads outside a transaction (so the write lock is not held while audits are counted) and compare and set each move: a decision made on a state another process has changed since is dropped. `set_version` stays for tests and migrations. Event kinds and order are unchanged, so the reference simulation and the three pinned workloads are byte-identical.
- **`Ledger.transaction()`.** One `BEGIN IMMEDIATE ... COMMIT` under the ledger's lock, so what it checks and what it writes are atomic across threads and processes; nested calls join the outer one. Events written inside commit with it and reach the listeners (the log) only after the commit, never for a transaction rolled back, and a rollback invalidates every cache a write inside refreshed. A writer that commits by itself inside raises at the end instead of splitting the transaction silently.
- **One module for manual changes, shared by HTTP and CLI** (`ratchet/admin.py`): `rollback`, `retire`, `promote` (to a canary stage or to live, optionally loading the adapter into vLLM first, outside the transaction), `set_flag`, `pin_task`, `unpin_task`, `tick`, and reads (`versions`, `flags`, `audit_log`). Each checks its reason (3 to 500 characters, one line, redacted because it lands in the release log) and its actor (`api:<admin key name>` or `cli:<OS user>`, never a key), checks the move against an explicit table (`MOVES`), and writes the change, an `admin_actions` row (time, actor, action, target, reason, before and after as JSON, the call's request id) and an `admin` event in one transaction. A refused or stale move raises `AdminConflict` (409, CLI exit 1); a call that changes nothing writes nothing.
- **The transition table.** canary to rolled back, retired, another share or live; live to retired; shadow to retired or canary; a rejected, rolled-back or retired version or a candidate to canary only with `force`. Nothing becomes live except a canary; a version without a golden eval (no calibrated threshold) is never promoted; one version in flight at a time.
- **Runtime switches** in a `runtime_flags` table (`student_disabled`, `releases_frozen`, `training_paused`, `audit_rate`) and runtime pins in `task_overrides`, read through `Ledger.flags()`: a `RuntimeFlags` snapshot rebuilt only when this connection wrote one of the tables (TEMP triggers, as for the routing snapshot) or another process committed (`PRAGMA data_version`), so the CLI's change applies on the gateway's next request without a restart, for one `PRAGMA` per request. A row written by hand that does not parse is ignored, never an error on the request path.
  - `student_disabled`: `Ratchet._pick_version` returns no version; the teacher answers (route `student_disabled`), its answers are stored as on a cold start, and no shadow sample is drawn. The kill switch stops every student call and changes no version.
  - `releases_frozen`: the gate starts no version taking traffic and gives none more (no shadow to canary, no canary advance or promotion; a cold-start candidate shadows the teacher instead of taking 10%); rollbacks, rejections and the live alert always run.
  - `training_paused`: `run_night` writes a `skip` event before anything else.
  - `audit_rate`: replaces `RATCHET_AUDIT_RATE` (0 to 1); the audit draw is made either way, so the random stream does not depend on it. 0 while a canary is in flight needs `force`, and with the rate at 0 the gate starts no new canary (it could neither advance nor be rolled back).
  - Runtime pins: `Ledger.flags()` publishes the pinned names to `tasks.OVERRIDES` (one assignment, like `REGISTRY`), and `tasks.get` / `tasks.effective` return a pinned copy of the registered task (its spec's `spec_hash` kept: a pin changes who answers, not how answers compare, so unpinning needs no re-score). The router sends it to `_teacher_only` and Night School leaves its rows out, both through the existing pinned paths (invariant 10). Only a registered operator task (built-in, file or API) can be pinned.
- **Endpoints** under `/ratchet/admin/` (an `admin` prefix in `access.py`, reads included, through `gateway._admin`), each answering the target's state before and after: versions, flags, audit log, rollback, retire, promote, student disable/enable, releases freeze/unfreeze, training pause/resume, `PUT settings` (audit rate), task pin/unpin, and tick (recorded as an admin action, its reason optional). `/ratchet/stats` gains `controls`; `GET /ratchet/tasks` gains `runtime_pinned`.
- **CLI** `python -m ratchet.admin versions | rollback | retire | promote | flag | pin | unpin | audit-log` on `RATCHET_DB`; it opens an existing ledger only and installs the tasks file and the stored API tasks before a pin, so it sees the gateway's registry.

## Alternatives considered

- **A process-wide lock file or a single tick owner.** It would serialise the two ticks but not an admin, and a crashed owner would hold releases. Compare-and-set needs no coordinator and covers every writer.
- **Re-read and compare in Python, then write.** Without the `WHERE` on state and share inside the write transaction, another process can still commit between the read and the write.
- **Hold one transaction for the whole tick.** Simpler to reason about, but it holds the write lock (and every request's ledger write) while the gate counts audits; the steps' moves compare and set instead, and `admit`, which is short and runs once a night, takes one transaction.
- **Environment variables for the switches.** They need a restart and say nothing about who changed them or why.
- **A runtime pin as a spec change through the tasks API.** It would change the task's `spec_hash` and send it to recalibration when unpinned, and it cannot pin a built-in or file task. A separate override keeps the spec as written.
- **Record admin actions only as events.** Events are free text; `admin_actions` keeps the actor, target, reason and both states as data for the audit log and for a later tamper-evident ledger to chain.

## Consequences

- Manual changes are recorded, checked and atomic; RUNBOOK's manual interventions use the CLI and the API, and raw SQL is gone from it.
- The two ticks and an admin can run at once: each decision is made once. A tick's decision on stale data is dropped and taken again on the next tick, with fresh evidence.
- Every request reads the switches (one `PRAGMA data_version` under the ledger's lock); a change is seen on the next request, also across processes.
- A runtime pin holds while the task is registered; deleting the task's spec leaves the override row, which applies again if the name is registered again (`unpin` removes it).
- `admin_actions` rows are written directly; a tamper-evident ledger, when it lands, appends them through its chain.
