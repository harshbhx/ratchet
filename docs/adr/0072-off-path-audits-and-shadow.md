# ADR 0072: Off-path audits and shadow

- Status: Accepted
- Date: 2026-10-21

## Context

A code reading of `Ratchet.handle` found three kinds of work on the request path that do not change the answer the client gets:

- **The teacher's audit** of a served student answer (5% of student-served requests in live mode, at least 10% in mock mode): a whole teacher call (the mock teacher simulates 2.4 s; Nemotron Ultra takes seconds), against a few hundred milliseconds for the student.
- **The shadow candidate's samples**, on every request while a version is in shadow.
- **The teacher's arbitration** when the shadow disagrees with an answer the live student served.

So the p95 of student-served requests was the teacher's latency whenever audits ran or a shadow was in flight, against NFR-1 (p50 under 1 s for student-served requests; the whole point of the cascade is that the student answers fast). The work cannot be skipped: audits are the release gate's live signal (canary rollback, the live alert), audits and arbitrations are free training data, and the shadow's verdicts decide admission to canary.

What must not change is what that work measures. Two properties matter for the release statistics:

1. **The same requests are audited.** The audit is a random sample of student-served answers; Wilson bounds over it assume nothing else chose which answers were checked.
2. **Nothing counts before it is known.** A count of audits that included ones still running would claim evidence the gate does not have.

## Decision

- **A bounded sidecar** (`ratchet/sidecar.py`, `SideCar(workers, max_queue)`): daemon threads started on first use and a queue of at most `RATCHET_SIDECAR_QUEUE` (1000) waiting jobs. A request takes a place before it logs its row (`reserve()`, never blocking) and then submits its job or gives the place back. `RATCHET_SIDECAR_WORKERS` defaults to 4 in live mode and 0 in mock mode, where nothing changes. Each job runs in a copy of the request's context variables, so log lines, failures rows and the seen window (ADR 0071) still name the request. Each job also keeps the request's messages until it ends, so the request text queued and running jobs hold is bounded as well (`max_bytes`, 64 MiB, measured by `job_bytes` as Python stores the strings): a count bound alone would let a thousand long requests (120,000 characters each by default) hold half a gigabyte. A reservation past either bound is refused the same way.
- **One job per request, the same calls in the same order.** The router's audit and shadow code moved into `_audit` and `_shadow`, which the request path and the job both call. One job, not one per check, because the shadow depends on the audit: its reference is the counted audit's answer, and a failed audit stops its arbitration. The job runs the audit first, then the shadow with the counted audit (or the escalation's teacher answer, or an audit that ran on the request path because the queue was full) as its reference, exactly as the request path did, and stores teacher answers through `_store_example` (INV-2, INV-12, INV-16). INV-15 holds unchanged: a failed audit is no audit and stops the arbitration; a failed shadow sample leaves no shadow record; a failed arbitration leaves the disagreement unarbitrated.
- **Every random draw stays on the request path, in the same order**: the canary pick, then the audit draw. Which requests are audited does not depend on the queue.
- **Pending is explicit in the row.** The request's row is logged first with `audited` 1 and `audit_agree` NULL for a pending audit, `shadow_version` set and `shadow_serve` NULL for a pending shadow. `Ledger.update_request(id, ...)` finishes it: under the ledger's lock, a verdict only where it is still pending (written once), costs and tokens added one call after the other in the request path's order (SQLite's REAL arithmetic is IEEE double, so the finished row holds the same floats an inline run writes), `stored` only raised, and after a teacher audit the baseline the audit prices. Any other column is refused before anything is written. Those writes touch no column a hot-path cache keys on, so they are left out of the `requests` generation the caches compare (ADR 0060).
- **The gate counts no pending check.** `version_live_quality` counts audits with a verdict only (`COUNT(audit_agree)`, `AVG(audit_agree)`); its incremental tally keeps the ids of pending audits it read and settles them on each call. `shadow_quality` already reads only rows with `shadow_serve` set, and `stats_by_day`'s audit agreement averages verdicts only. Before this change no row was ever `audited` 1 with `audit_agree` NULL, so every number the gate computed before is unchanged.
- **A drawn audit is never dropped.** The last tenth of the queue (`audit_places`, at least one once there are two places, and a tenth of the byte budget) only a job carrying an audit may take, so shadow work alone cannot crowd audits out; when even those places are taken, the audit runs on the request path, as before (`audits_inline`, a throttled `sidecar_inline` event, `ratchet_sidecar_full_total{outcome="audit_inline"}`). Dropping it would make the audited sample depend on load: busy hours, often a different mix of requests, would be under-sampled, and the canary's bound would describe quiet hours.
- **A shadow without a place is skipped**, counted per version (`shadows_dropped`, a throttled `sidecar_dropped` event). The shadow is a pre-filter before an audited canary whose rollback still sees every drawn audit, and running it inline under overload would put the full shadow cost back on the request path exactly when the gateway is busiest.
- **The response says what is pending.** `ratchet.overhead_pending: true` (present only then), with `cost_usd`, its split and `all_teacher_cost_usd` describing serving the answer. `usage` never included the checks (ADR 0018), so it is unchanged. The job adds its cost to `ratchet_cost_usd_total` and, for an audited request, the baseline to `ratchet_baseline_usd_total`, and writes one `offpath` log line under the request's id.
- **The arbitration gives up sooner; the audit does not.** Off the request path the arbitration's retries end after 60 s (`ARBITRATION_DEADLINE_S`, through a `deadline_s` that can only shorten the provider's retry deadline): a worker should not be held for the full 180 s serving deadline, and an unarbitrated disagreement counts against the shadow, so a shorter wait can only make the shadow look worse. The audit keeps the teacher's deadline: a failed audit leaves the sample, and if slow answers (often the hard requests, where the student is wrong) failed more often, the audited precision would be biased upward. Shadow jobs use the shadow's own breaker, as on the request path.
- **Only gateway requests go off the path.** `RequestMeta.offpath` (default true) and a sidecar with workers that is not closed decide it. Scout's agents, the simulator and the mock warm-up pass no meta: Scout's budget guard sums `Result.cost_usd` (INV-11), and the seeded simulations keep every call in its old order, so the reference simulation and the three pinned workloads stay byte-identical whatever the settings.
- **Shutdown drains, then gives up.** The app's lifespan calls `Runtime.shutdown()` once the server stopped taking requests: wait up to `RATCHET_SIDECAR_DRAIN_S` (10 s), then give up on the jobs still queued. Their rows stay pending, which every statistic ignores, and one `sidecar_dropped` event counts them per version; a running job finishes in its thread. After that, checks run inline again. A job handed over after the drain gave up is refused, and the request (still on its own path) runs it itself. The demo VM's Compose file gives the container 20 s to stop.

Invariants 2, 4, 6, 7 and 15 are untouched.

## Alternatives considered

- **Drop work when the queue is full** (the first version of this design): an audit sample that thins out under load biases the release statistics, which is what the audits exist to measure. Audits get reserved places and an inline fallback instead.
- **Run the shadow inline when the queue is full, like the audit.** It keeps shadow statistics free of load-dependent gaps, at the cost of putting the shadow's samples and arbitrations back on the request path under overload. The canary's audits are the decision that rolls back; the shadow only admits to it. Skips are counted per version, so an operator sees when a shadow's evidence comes from part of the traffic.
- **Shorten the audit's deadline too, to free workers sooner.** Rejected for the bias above.
- **A process pool or an external queue** (Redis, a jobs table). The jobs are I/O-bound teacher calls that need the router's breakers, the ledger connection and the request's context; threads share them. A durable queue would also have to persist request text to run an audit later, which INV-12 forbids. Jobs lost to a crash leave rows pending, which every statistic already ignores.
- **Mark abandoned audits `audited=0` at shutdown.** A row that was drawn and never checked is a different fact from an audit that failed; leaving it pending keeps that visible, and a crash leaves rows pending anyway.
- **Return the final cost later through a webhook or a second call.** No OpenAI client would read it; the ledger and `GET /v1/ratchet/requests/{id}` have the final row once nothing is pending.

## Consequences

- An audited student-served request costs its client the student's latency only; the teacher's latency moves to `ratchet_sidecar_job_seconds`, which is how long its row stays pending. Under overload the audits come back onto the request path (`ratchet_sidecar_full_total{outcome="audit_inline"}`), never out of the sample.
- A row can be pending. Anything that counts audits or shadow verdicts must count verdicts (`audit_agree IS NOT NULL`, `shadow_serve IS NOT NULL`), as `version_live_quality`, `shadow_quality` and `stats_by_day` do, and a reader that freezes a row's cost or verdict (a sealed record, a replay of a version's traffic, a spend meter) must read it once nothing is pending, or count what the job adds when it ends (`update_request` is the one writer). Which requests were drawn for an audit stays on the request path, so a probability of observing a label computed there is unchanged.
- The response's `cost_usd` is the serving cost when `overhead_pending` is set; the ledger, `/ratchet/stats`, the cost report and `GET /v1/ratchet/requests/{id}` have the final cost once the job ends, and the metrics count each cent once (the request its serving cost, the job the rest).
- Live-mode tests that read a row's audit or shadow columns right after a request wait for the sidecar first (`r.sidecar.drain(timeout_s)` on the `Ratchet`), or pass `RequestMeta(offpath=False)`, or build the `Ratchet` with `SideCar(0)`.
- Mock mode, Scout, the simulator and the reference runs behave exactly as before.
