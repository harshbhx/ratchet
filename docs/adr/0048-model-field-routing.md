# ADR 0048: The model field names a task, never an upstream model; `/v1/models` lists the tasks; an Azure-style route

- Status: Accepted
- Date: 2026-10-20

## Context

Ratchet's task decides how answers are compared, which threshold the student is held to and which examples a night trains on. Until now a request chose its task with the `X-Ratchet-Task` header or `metadata.ratchet_task`, and ignored its `model` field. That left out every client that can set neither: a framework or a no-code tool whose only setting is the model name, a client with a hard-coded `gpt-4o-mini`, an Azure OpenAI client that puts its deployment in the URL. Their requests all landed in `default`, which compares whole answers, so a structured task's traffic was distilled and calibrated under the wrong rules.

`GET /v1/models` returned one item without `created`, which the OpenAI SDK's `Model` requires, and `GET /v1/models/{id}` was a 404, so `client.models.retrieve(...)`, which some frameworks call at startup to check a model, failed.

The `model` field is also the field a client would use to pick an upstream model. Ratchet must never let it: the teacher is licensed for distillation at startup (INV-1), and a request that could name `gpt-4o` and have it called would turn a client's string into a closed-model call, with its answers then offered as training data.

## Decision

- **One resolution order** (`openai_compat.resolve_task`, pure, no I/O): the header; `metadata.ratchet_task`; a model id `ratchet/<task>` (or `ratchet:<task>`); a model alias (`RATCHET_MODEL_ALIASES`, `gpt-4o-mini=ticket-triage,...`); the first registered task whose match rules all hold; a slot for the structured-outputs item's json_schema auto task; with `RATCHET_AUTO_TASK=system_prompt`, an auto task per first system message; `default`. The response says which rule chose (`ratchet.task_source`) and the task (`ratchet.task`, `X-Ratchet-Task`). The header still wins over everything, so existing clients see no change.
- **The model field names a task and nothing else.** Every teacher call sends `Settings.teacher_model` (or the licensed fallback teacher's model), every student call its adapter name; the request's `model` is read only by the resolver and echoed back as `ratchet.requested_model`. The response's `model` stays the model that served. Proposed as an invariant (lane C2), proved by a live-mode test whose fake teacher records every body.
- **Unknown model ids, two policies.** `RATCHET_MODEL_POLICY=lenient` (default) serves an id Ratchet does not know as `ratchet` and says so in `X-Ratchet-Model-Alias` (UTF-8 percent-encoded except for visible ASCII, spaces and `%` included: h11, the HTTP/1.1 server uvicorn runs, refuses a header value that starts or ends with a space and would drop the connection after the request was served and billed; at most 256 characters, never half an escape), so a client with a hard-coded model name works unchanged. `strict` answers 404 `model_not_found` in OpenAI's words before anything is logged or billed. A malformed id in Ratchet's own namespace (`ratchet/bad name`) is a 404 under either policy: whoever writes `ratchet/` means a task, and serving it as `default` would distill its answers under the wrong rules. A missing or empty `model` counts as `ratchet` under both, as before. An unregistered task named through the model field follows `RATCHET_UNKNOWN_TASKS` exactly as a header does, with `param: "model"` in its 400.
- **Match rules** (a task spec's `match`, accepted since the task registry but read by nothing until now): `system_prefix` (`str.startswith` on the first system or developer message, its text parts joined as normalisation joins them), `schema_name` (`==` on `response_format.json_schema.name`) and `tools` (set equality on the names of `tools` and legacy `functions`). Every rule a task declares must hold; tasks are tried in registry order (built-in, file, API and auto); a task whose `clients` do not name the key is skipped, so a match never turns a request that named no task into a 403. Plain comparisons, never a pattern, so no request can make matching slow; each request feature is read at most once.
- **Auto tasks per system prompt** (opt-in). `auto-sys-` and 10 hex digits of SHA-256 over the first system message: the same prompt always gets the same task, and the name holds a digest, never the prompt's text (INV-12). A new one is a task without fields (whole answers compared, like `default`), source `auto`, never pinned. It is registered and stored in the ledger's `tasks` table (`updated_by` `auto`), so a restart and Night School register it again, only after the request passed its quota, under the registry lock (one registration however many requests race). At `RATCHET_MAX_AUTO_TASKS` (200; at most 250, half the registry, and at most 50 in mock mode) auto tasks, or when the registry has only its last 50 slots free, requests with a new prompt get `default` and one `auto_task_cap` event is logged per ledger, once such a request is admitted. The free slots keep request traffic from filling the registry and locking the admin API out (auto tasks are stored, so they come back at every restart); an admin can delete an auto task to free its place.
- **`/v1/models` lists what a client can send**: `ratchet`, `ratchet/<task>` for every registered task the key may use and, unless `RATCHET_UNKNOWN_TASKS=reject`, every unregistered task its own requests named in the last 30 days (500 at most, most recent first), and every alias whose task it may use. Each item has OpenAI's `id`, `object`, `created` (when the task was first seen, else when the process started) and `owned_by: "ratchet"`, plus a `ratchet` block (task, pinned, format, the fields that must agree, the live version that serves it, `alias_of`). With keys on, an auto task is listed only to a key whose own requests used it lately: its name is a digest of a client's system prompt, and a short prompt's digest can be checked against a dictionary. `GET /v1/models/{id}` looks up that one id and returns it, or a 404 `model_not_found`; it also finds `ratchet/<name>` for an unregistered task name no request used yet unless `RATCHET_UNKNOWN_TASKS=reject`, because a chat completion naming it would be served under either policy. `Ledger.recent_tasks` walks the `(task, ts)` or `(client, task, ts)` index one distinct task name at a time (three probes each), so the call that holds the ledger's lock costs what the number of task names costs, not a pass over every request; past 2,000 names it falls back to one aggregate over the covering index. With keys on it counts only the caller's requests, so one client's ad hoc task names are never shown to another.
- **Azure OpenAI's URL shape**: `POST /openai/deployments/{deployment}/chat/completions` runs the same handler, checks and envelope, with the deployment as the task (an alias, `ratchet`, or a task name; anything else 404) and the body's `model` not read; `api-version` is accepted and ignored. Keys are also read from Azure's `api-key` header (after `Authorization: Bearer` and `X-API-Key`), on every `/v1` route.

## Consequences

- A LangChain `ChatOpenAI(model="ratchet/ticket-triage")`, a no-code tool, a hard-coded `gpt-4o-mini` with an alias, and an `AzureOpenAI` client each reach the right task without code changes; the SDK's `models.list()` and `models.retrieve()` work.
- Match rules in existing task specs now route requests that name no task. The built-in tasks have none, so with the default settings every request that sent no header or metadata is `default` as before; the pinned reference simulation and the three reference workloads call the cascade directly and are byte-identical.
- `owned_by` in `/v1/models` is `ratchet` instead of `you`.
- Auto tasks grow the registry; the cap bounds them to half the registry's 500, they never take its last 50 slots, and the admin API can replace one (an API task may replace an auto task) or delete one.
- Every OpenAI-compatible route (`/v1/*` and `/openai/*`, `gateway.API_PREFIXES`) runs or lists the paid cascade, so the demo VM's Caddy edge guard (`RATCHET_API_GUARD=guarded`) covers both prefixes; a test checks that every such route falls under a guarded path.
- The structured-outputs item adds its json_schema auto task at rule 6 and is expected to share `RATCHET_MAX_AUTO_TASKS` and the `auto_task_cap` event; per-key task scopes (`RATCHET_KEY_LIMITS`) belong to the rate-limits item.
- Strict mode refuses a client that sends a model id Ratchet does not know even when a header names the task: strict means every id outside Ratchet's namespace must exist. Inside it, `ratchet/<task>` names a task, and an unregistered one follows `RATCHET_UNKNOWN_TASKS` for chat completions and `GET /v1/models/{id}` alike.
