# ADR 0042: Structured outputs: a response_format is a contract, and a json_schema names an auto task

- Status: Accepted
- Date: 2026-10-21

## Context

Since v0.5 the gateway forwards a client's `response_format` to the teacher and the student ([ADR 0017](0017-generation-parameters-by-role.md)), but nothing checked the answers against it:

- A student sample that broke the schema could still win the vote and be served, and a teacher answer that broke it could become a training example and a golden reference.
- The task decides which parts of an answer are compared. A structured-outputs client (the OpenAI SDK's `client.chat.completions.parse(response_format=Model)`) names no task, so its requests fell to `default`, which compares whole answers: a free-text field (`reply`, `summary`) in every answer kept samples from agreeing, and the student never served them.
- The served text kept a code fence or a sentence around the JSON, so `.parse()` raised a validation error on a correct answer.
- Some OpenAI-compatible servers refuse `response_format` json_schema with a 400, which failed every such request.

## Decision

- **A `response_format` is a contract on every answer of its request** (`schema_tasks.contract_for`). `json_object`: the answer is one JSON object. `json_schema`: the answer is JSON that matches the schema, checked by `ratchet/jsonschema_lite.py`, a standard-library validator for the strict subset (`type` with null, `properties`, `required`, `additionalProperties`, `enum`, `const`, `items`, `prefixItems`, `anyOf`, `oneOf`, `allOf`, local `$ref` with a loop guard, item, length and numeric bounds). Unknown keywords are ignored; a `pattern` is never run, because a client's regular expression on the request path would let one request make the gateway slow, and `additionalProperties: false` is not enforced beside `patternProperties` for the same reason. A check has a step budget (`MAX_STEPS`, about 0.3 s at worst) and an answer it cannot finish checking is invalid, never valid; the router remembers each answer's result by its digest, so one answer is checked once per request.
- **The contract binds to the request's task** (`tasks.Task.bound`): a copy for that request with the same rules and `spec_hash`, so thresholds, per-task records and the registry see the same task. Under a bound task an answer that breaks the contract is invalid (`schema mismatch at <path>`, `invalid answer`): a student sample gets no vote, a teacher answer is not stored and is not an audit or a reference (invariant 16). The served text is the JSON the answer holds (`tasks.json_span`: the substring the model wrote, after reasoning and a fence are removed, never re-serialised).
- **Night School holds a stored row to the contract it was stored under** (`tasks.for_row`): `dataset.rows` and `cascade_eval` bind the row's task to the `response_format` in `examples.params`, as the router bound the request, so the golden eval grades the student exactly as production would (invariant 6) and an answer that breaks its schema is never a training target.
- **Which task: a registered name wins.** An `X-Ratchet-Task` header or `metadata.ratchet_task` naming a registered task keeps it; the schema is forwarded and checked on top of its fields. Otherwise a json_schema request gets an **auto task**: named by the header or metadata when they give an unregistered name (under `RATCHET_UNKNOWN_TASKS=distill` only; `teacher` and `reject` govern the names clients make up), else `auto-<slug of json_schema.name>-<first 8 hex digits of SHA-256 over the canonical schema>`, the same whatever the key order. Its fields come from the schema (`schema_tasks.derive`): enums are labels, booleans `bool`, integers `number` (exact), numbers `number` (relative tolerance 1e-6), `date` and `date-time` strings `date`, identifier formats (`email`, `uuid`, `uri`, `ipv4`, `hostname`) exact `text`, arrays of those a `set`, arrays of objects `records`, nested objects dot paths (at most 4 levels and 64 fields); free text and consts are ignored; required follows the schema, and a null the schema allows is `nullable`. A property's `x-ratchet` annotation (`{"compare": "text" | "ignore" | "ordered", "abs_tol": n}`) includes or excludes it; every key starting with `x-ratchet` is stripped before any model sees the schema or an example stores it.
- **Auto tasks are registered and stored** (source `auto`, never pinned, `updated_by` null) in the ledger's `tasks` table, so a restart and `python -m ratchet.live night` find them (`taskspec.install`). Registration runs under the gateway's task lock, so it never interleaves with the admin API, which may replace or delete an auto task. At most `RATCHET_MAX_AUTO_TASKS` (200) are registered; past that, and for a schema with no comparable field or a derived spec the redactor would change (an enum of email addresses: the `tasks` table holds rules, never personal data), the request gets an unregistered task of that name, which `RATCHET_UNKNOWN_TASKS` decides about, so a free-text-only schema is never distilled silently under `teacher` or `reject`. `json_object` without a schema binds the named task or `default` (canonical JSON compared).
- **One repair** (`RATCHET_SCHEMA_REPAIR=1`, the default): a complete teacher answer that breaks the contract gets one more call to the same teacher with the same parameters, its own answer as an assistant turn and a user turn `Your previous answer did not match the schema: <errors>. Reply with JSON only.` The errors name schema paths and expectations, never the answer's values. A user turn, because many chat templates refuse a system message after the first turn. The repair conversation is never stored: the example keeps the request's own messages and the repaired answer, which is still the teacher's (invariant 2). Both calls are paid for in `cost_usd` (the replaced answer under `usage_breakdown.repair`); the baseline is the served answer's. A cut-off answer, `n` > 1 choices, an open breaker and a failed repair call (an optional call: `repair_errors`, a throttled `schema_repair_error` event) skip the repair. An answer still invalid is served with `ratchet.schema_valid: false` and not stored.
- **A teacher that refuses json_schema** (a 400 whose `param` or message names `response_format` or `json_schema`) is asked once more, within the same breaker slot, with `{"type": "json_object"}` and the schema appended to its leading system message (`schema_tasks.downgrade`); the answer is still checked against the schema, and the example stores the client's format. That schema then goes the json_object way directly; once one endpoint has refused `JSON_SCHEMA_STRIKES` (3) different schemas, every schema does, and the provider says so (`supports_json_schema = False`). One `json_schema_fallback` event per ledger for the first refusal, and one for turning it off. `scripts/day1_check.py` probes json_schema and warns on a refusal.
- **What clients see.** The `ratchet` block gains `task` (the resolved task's name) and `schema_valid` (every choice meets the contract; null without one). `finish_reason` is `length` for a cut-off answer, so `.parse()` raises `LengthFinishReasonError` rather than a validation error. `/ratchet/stats` `tasks[]` adds `compare_keys` and `compare_source` (`schema` for an auto task, `registry` for a built-in, file or API task, null for an unregistered name).

## Consequences

- SDK structured outputs distill without any task configuration, and the student is compared on the fields a schema implies rather than on free text, so it can serve them.
- An auto task is a real registry entry: it appears in `GET /ratchet/tasks`, has its own per-task threshold (FR-14.1) and can be replaced by an operator's API spec or deleted (its examples stay). A schema change is a new auto task with its own data: the hash names the schema.
- Redaction still applies to stored answers. A placeholder replaces an enum value only when the value itself looks like personal data (an email address), and then the stored answer no longer matches the schema and is not stored (`invalid after redaction`).
- The step budget bounds the cost of a hostile schema, and the memo keeps a large schema to one check per distinct answer, but a client with a key can still make each of its requests spend a fraction of a second of CPU; the request limits on schema size and depth stay the first line.
- Rows stored before this change with a `response_format` are graded under it from the next night on: an old answer that breaks its schema leaves the training set (`skipped_invalid`) and the golden set (`golden_invalid_refs`). The three pinned reference workloads send no `response_format` and do not move.

## Alternatives

- **Derive the fields from the stored schema in Night School** instead of storing the auto task. The stored schema has its `x-ratchet` annotations stripped, so the fields would differ from the router's; storing the task keeps one source of truth, and `for_row` takes only the contract from the stored conditions.
- **Remember a json_schema refusal for the endpoint at once**, as the spec first said. A grammar engine may refuse one client's schema (a keyword it cannot compile) and take every other, so one bad schema would have downgraded every client; three strikes keep that to the refused schemas.
- **A repair note as a system message**, as the spec first said. Chat templates that take one leading system message refuse it; a user turn after the assistant's answer works with every template.
- **The `jsonschema` package.** A dependency for a subset the request path needs, without a step budget, and it runs `pattern`.
- **Re-serialise the served JSON.** It would change the model's text (key order, number spelling, escapes) and break the token logprobs' alignment; the substring is what the model wrote.
