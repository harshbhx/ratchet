# ADR 0091: Human labels as a provenance source: feedback, corrections and labelled-data import

- Status: Accepted
- Date: 2026-10-21

## Context

Every training target in Ratchet was a teacher's answer (invariant 2), and every teacher went through the license registry (invariant 1). Two kinds of ground truth were missing:

- **People who use the answers.** A support agent sees that a ticket was routed to the wrong queue; a reviewer fixes an extraction. Nothing let a client say so. The response's id was random and stored nowhere, request rows hold no text, and there was no endpoint for a verdict.
- **Labels the customer already has.** Teams moving from OpenAI fine-tuning (persona P4) arrive with JSONL files of hand-written labels, or with outputs of an open model they ran themselves. The only way in was through the gateway, as teacher traffic.

Both have to come in without opening the doors the invariants close: the student's own text must never become a target (model collapse), a closed model's outputs must never train anything (its terms forbid it), and pinned tasks, storage opt-outs, redaction and the held-out golden set must hold for these labels as for a teacher's.

## Decision

**Human is a provenance source, not a teacher.** `licenses.SOURCES` holds `human`, with license `customer-provided labels` and the note "written or approved by the customer; the customer attests ownership". It is not in `REGISTRY`. `licenses.lookup_source(model)` reads the registry, then `SOURCES`, and is what readers of stored examples use: `dataset.rows`, `dataset.counts_as_train` and the BOM's sources. `require_distillable` never looks a `SOURCES` name up as a license (it refuses one by name, with a message that says why), so `RATCHET_TEACHER_MODEL=human`, or a fallback teacher of that name, stops startup in any case, and a `RATCHET_TEACHER_LICENSES` entry may not be called `human` either. A human label is stored with `teacher_model` `human`, `verified` 1 (a new column: a person wrote the label) and `origin` `feedback` or `import`.

**Request ids.** The gateway gives every chat request an id, `req_` and 32 hex digits, logged in the new `requests.request_id` (indexed) and returned as `ratchet.request_id`; the completion id is `chatcmpl-` and the same digits. This is the minimum of the request ids another work package builds in full (middleware, a context variable, `x-request-id` on every response, client request ids): the same column name, index name, format and response field, so the two merge into one.

**Verdicts.** `POST /v1/ratchet/feedback` takes `{request_id, verdict: correct|incorrect}`. An API key reaches only requests logged under its name; another key's request, an unknown id and one whose row retention folded all get the same 404, so the endpoint is not an oracle. With API keys off it is open, like chat completions. A new `feedback` table keeps one row per request (ids, names and flags, never text), copying the request's task, version, `served_by` and route so the statistics outlive the request row. A later verdict replaces the earlier one.

Verdicts feed `human_agreement` per task and a **human precision** per version, over the answers the version served itself (route `student`; a degraded stand-in is not its choice), with 95% Wilson bounds. Human precision is reported and alerted on, never used to promote or roll back: clients report what they notice, so the sample is biased, and the audited precision (a random sample the teacher grades) stays the release signal. The alert is checked after every verdict, and a fixed-sample bound such as Wilson's, looked at that often, raises false alarms far more often than its level. So it uses the anytime-valid rule of the release gate's e-process ([ADR 0025](0025-anytime-valid-release-gate.md)): once a version has at least `min_audits` verdicts and the mixture e-value against "human precision is at least `live_floor`" (`stats.log_e_bernoulli`, side `below`) reaches 1 / `feedback.ALERT_ALPHA` (40, for 0.025, the one-sided level of the reported Wilson bound), one `human_alert` event says so (a meta row keeps it to once per version, across restarts). By Ville's inequality the false-alarm rate stays under 2.5% however many verdicts arrive. The check runs when a verdict is written, for that version only, so `Ratchet.handle` and `ReleaseGate.tick` do not change.

**Corrections.** An `incorrect` verdict may carry `corrected` and the request's `messages` (request rows hold no text, so the client sends them), with the request's conditions (`response_format`, `tools`, `tool_choice`, `stop`) and end user (`user`, `safety_identifier`). The fields go through the chat route's own validation and normalisation, and the conditions through the serving teacher's allowlist (`feedback.conditions`), so a correction of a request has the same example hash as the teacher's answer to it. The label is cleaned as an answer is served, checked against the task's spec (a 400 when invalid), redacted as a teacher answer is (invariant 12), and stored in the split its hash gives (invariant 3). A `correct` verdict stores nothing: the gateway never kept the student's text, and a verdict is not a label (invariant 2).

A correction is kept out, with the reason in the response and the verdict still recorded, when the request was under a storage opt-out, when one applies now (`Ratchet.store_opt_out`: zero retention, a no-store task, the key's `store=0`, a no-train end user), when the task is pinned (invariant 10), when the request was the teacher's alone (an unregistered task under `RATCHET_UNKNOWN_TASKS` `teacher` or `reject`, or a teacher-only request), and when `RATCHET_FEEDBACK_CORRECTIONS=0`. A request that named an end user needs every identifier it carried with the correction. The request row keeps the keyed hash of the identifier it was attributed to (`end_user`) and, when it carried both `user` and `safety_identifier`, of the second one (`requests.end_user_secondary`, the same HMAC in the same scope, logged by the router from `RequestMeta.end_user_secondary`); each value the correction sends must match its hash, and a correction that sends only one of two is a 400. Only the values find a registration made with either identifier, or an admin's every-client one, so a correction can never store an opted-out end user's prompt. The second hash is identifying data like the first: the requests export leaves it out, and erasing the end user by either identifier clears both. Rows logged before the column existed hold only the attributed hash, so only that identifier is required there. One correction per request: the same messages and conditions again replace it (a fix), others are a 409, and so is a `correct` verdict after a stored correction.

**Which label wins.** On an existing example a label replaces the stored one only when it is stronger: teacher (0) < a client's correction (1) < an operator's import (2), or as strong and from the same writer (the same request's correction again; the operator's later import). So a human label beats a teacher's on the same hash, a later teacher answer only bumps `seen`, an import beats any correction, and one client's correction never overwrites another's. `Ledger.add_example` gains `verified`, `golden_only`, `origin`, `replace` and `bump`; its defaults keep the router's behaviour, and the decision lives in `feedback.store_label`, the only new caller (the INV-2 allowlist in `tests/test_nightschool.py`). `seen` counts real requests only: a correction of a request whose teacher answer was stored, or that was corrected before, does not bump it, and when it lands on an example not stored yet (another variant of the prompt) that example starts at `seen` 0, not the column's default 1. Readers count 0 as 0 (`ledger.seen_count`; NULL in a row older than the column still counts once), so such a label never pushes a prompt to FREQUENT (invariant 3).

**Import.** `python -m ratchet.importer FILE --task T` reads OpenAI's chat fine-tuning JSONL (the assistant's answer last; earlier turns are context; a tool-call or weight-0 answer is refused) and Ratchet's own `train.jsonl`, whose task and provenance must match the run, so a teacher's exported outputs never come back as human labels. `--source human` needs `--attest`; `--source teacher:<model>` must pass `require_distillable`, and any id of a closed family (`licenses.closed_family`: `gpt`, `o1`/`o3`/`o4`, `claude`, `gemini`, the closed vendors) is refused with the clause of its terms quoted; every OpenAI family now carries the Section 3.3(e) note. An unregistered, pinned or no-store task and zero retention refuse the whole import before a row is read. Rows are validated and normalised as chat requests, cleaned, checked, redacted and deduplicated, in the file and against the ledger, without counting toward `seen` (an import is not an occurrence of the request: a stored example keeps its count, a new one starts at 0, so an imported variant never pushes a twice-seen golden prompt into training). One `import` event records the counts, the file's SHA-256 and the attestation (redacted, one line, at most 1,000 characters). `--dry-run` imports into an in-memory copy of the ledger, so it reports exactly what would happen; the file is opened read-only, so a dry run never creates a ledger at a mistyped path (it is refused) or migrates an older file. Each row's read, decision and write run in one write transaction (`Ledger.atomic`, `BEGIN IMMEDIATE`), so a teacher answer the gateway stores at the same moment cannot turn the import's label into a mere duplicate. A router alias (`openrouter/auto`) is refused too: the model that answered may be closed.

**Golden-only rows.** `--golden-only` stores rows in the golden split whatever their hash says, flagged `golden_only` (a new column, sticky on a duplicate): a human-verified golden set. `dataset.rows` holds them out even past FREQUENT, and every other variant of their prompt too (the trainer sees only the messages, so a variant in train would teach the held-out prompt). A golden-only row is refused (`trained`) for a prompt that may already have been trained on, a variant in the train split or one seen FREQUENT times, because it would not be held-out evidence (invariant 6). The check reads that one prompt (`Ledger.prompt_status`) inside the transaction that writes the row, so a variant the gateway stores while a long import runs is seen. This is the one place a split is not the hash's; every other label keeps invariant 3.

**BOMs list human labels apart.** The ledger's `/ratchet/bom` and each adapter's signed BOM keep `sources` for teachers and add `label_sources` (per source: license, note, examples, examples by origin). `training.targets` reads `teacher answers and customer-attested human labels` when human labels are among the targets, `golden.human_labels` counts human golden references, and NOTICE.md gets a Human labels section. An adapter without human labels gets the same `sources`, `training.targets` and NOTICE text as before, with `label_sources: []` and `golden.human_labels: 0` beside them; BOM v2 is unreleased, and no stored document is rewritten (invariant 14).

## Consequences

- Invariant 2 reads, amended (in AGENTS.md): training targets are teacher answers or customer-attested human labels, never student outputs, and a verdict is never a label. The related amendments to invariants 1, 3, 10 and 16 are in AGENTS.md too, with a new invariant 26 (human verdicts never promote or roll back a version).
- A client with a key can now choose labels, not just prompts (threat model T24). Bounds: its own requests only, one stored correction per request (so the request quota bounds them), the task's spec, redaction, the opt-outs, and `RATCHET_FEEDBACK_CORRECTIONS=0` for deployments whose clients should not write labels. The golden set and the audited release gate still catch broad damage; an operator's import outranks any client.
- The messages of a correction are the client's word: the request row holds no text to compare them with. Storing a keyed digest of every prompt was considered and rejected: it would fingerprint requests whose text is otherwise never kept (the opted-out ones), and it would not stop a client that can send any prompt anyway.
- Human precision is a second, biased quality signal that operators see and get alerted on; the release gate does not read it.
- A client can paste the student's own served answer into `corrected` with an `incorrect` verdict, and it is stored as a human label: nothing compares the two, because the gateway keeps no digest of the served text (the same reasoning as for prompts above). This is a client choosing a label it attests, not the system turning student output into a target, and the bounds of T24 apply; it is listed in the threat model as a residual risk.
- A label that replaces a teacher's on an existing training row adds no row, so it does not count toward Night School's new-data gate (`run_night`'s `min_new_examples`): corrections and imports that only relabel are trained on at the next night that has enough new rows (the runbook says so).
- When retention purged an example's text, a later duplicate restores it with that answer's label, teacher and license, and now also its `origin` (the restored label's own; NULL from the router), where before the stored origin was kept. The label and its origin now always describe the same answer; lane F's FR-16.8, which owns `examples.origin`, should keep that when the branches merge.
- New schema: `requests.request_id`, `requests.end_user_secondary`, `examples.verified`, `examples.golden_only`, the `feedback` table, three indexes. New setting: `RATCHET_FEEDBACK_CORRECTIONS`.

## Alternatives considered

- **Treat a correct verdict as a label.** Rejected: it would store student text (invariant 2).
- **Let verdicts promote or roll back versions.** Rejected: the sample is biased (invariant 26).
