# ADR 0062: Request ids end to end, a failures table with spent cost, structured logs without content, and Prometheus metrics

- Status: Accepted
- Date: 2026-10-20

## Context

Before this change an operator could not follow one request through Ratchet, or see what was failing:

- Nothing in `ratchet/` logged. The release log (`events`) records decisions and throttled error counts, but not requests.
- The completion id was random (`chatcmpl-` and 24 hex digits) and stored nowhere, so a client reporting a bad answer could not point at its ledger row, and a client's own `X-Request-Id` was dropped.
- A request that failed left no row: a teacher 502 after the student's three samples spent money that no report counted (NFR-3 says overhead is counted), and a quota 429, a wrong key or an unhandled error left no trace beyond a throttled event.
- There were no metrics to alert on (escalation ratio, student error rate, failed spend), only `/ratchet/stats`, which is a dashboard payload, not a time series.
- `ReleaseGate` retired the old live version on a promotion without an event of its own, so not every version transition was in the log.
- The OpenAI SDKs read `x-request-id` (as `response._request_id` and `error.request_id`) and `openai-processing-ms`; Ratchet sent neither.

## Decision

- **One id per request, made by the gateway.** `ObservabilityMiddleware` (plain ASGI, outermost, so 413s and streams are covered) gives every HTTP request a `RequestContext` (`ratchet/obs.py`): the id is always `req_` and 32 hex digits from a UUID4. It lives in the `obs.request_ctx` context variable, which `anyio.to_thread.run_sync` copies into the worker thread a route runs in, so code deep in the cascade names the request without the id being passed down. Every response gets `x-request-id` and `openai-processing-ms`; Starlette answers an unhandled error outside every middleware, so `_unhandled_error` adds both itself from `scope["state"]`. The completion id is `chatcmpl-` and the same digits; `ratchet.request_id` repeats it; the OpenAI error envelope on `/v1/*` gets `request_id` beside `error` (the error object keeps exactly OpenAI's four fields).
- **The client's id is kept, never trusted.** An `X-Request-Id` or `X-Client-Request-Id` matching `^[A-Za-z0-9._-]{1,128}$` becomes `client_request_id`, stored and logged beside the gateway's id; anything else is ignored without an error, so a header can never put arbitrary text into the ledger or a log line, and two clients sending the same id never collide.
- **Stored with the request.** `requests.request_id` and `requests.client_request_id` (SCHEMA and MIGRATIONS, index `requests_request_id`), filled from `RequestMeta`, which the gateway now passes to `handle` and `teacher_only`. Internal calls (Scout's agents, the simulator) have none.
- **Lookups.** `GET /ratchet/requests/{id}` (access level `dashboard`, ADR 0061) returns the request's `requests` row (metadata; the table holds no text) and its `failures` rows; a scrubbed read gets client pseudonyms. `GET /v1/ratchet/requests/{id}` (level `api`) returns only what the caller's key sent, and another key's request is a 404 with the same body as an id that never existed, so a key learns nothing about other clients. Both take the `req_` or the `chatcmpl-` form.
- **A failures table.** `failures (id, ts, day, request_id, client, task, stage, error, status, latency_ms, cost_usd)`, written by `Ledger.log_failure` (locked, columns and stage checked). `stage` is one of `teacher`, `student`, `audit`, `shadow`, `quota`, `auth`, `budget`, `rate`, `upstream`, `gateway`; `error` is the exception's class, status and code (`resilience.describe_failure`), never a message, which can quote request text or a URL. The router writes a row for every failure it swallows (a student call the teacher covered, a failed audit, shadow sample or arbitration) and for a teacher failure on the serving path; a refusal by an open breaker that spent nothing is written for the 1st, 11th, 21st ... time per stage only, so an outage cannot turn every request into a write. The teacher failure's row carries `cost_usd`, what the student's samples already cost, because no `requests` row holds it. The gateway writes a row for any other 401, 413, 429 or 5xx once the response is sent, in a worker thread, at most 120 per stage a minute (`FailureThrottle`), so a key guessed in a loop cannot fill the disk; validation 400s are counted in the metrics only. When the router decided a request's row (written or sampled out) it marks the context, and the gateway writes no second one.
- **Failed spend counts against the savings.** `Ledger.totals()` gains `failed_cost_usd`; `saved_usd = baseline - cost - failed_cost` and `savings_pct = 1 - (cost + failed_cost) / baseline`. Adding 0.0 changes no float, so a ledger without failures, the reference simulation and the three pinned workloads give exactly the numbers they gave. `/ratchet/stats` gains `errors.last_hour` (failures by stage since an hour ago). `days`, `tasks` and `clients` are unchanged.
- **Structured logs without content.** The `ratchet` logger writes to stderr through one handler `obs.configure` installs (replaced, never doubled, on a demo reset; the logger stops propagating so a host's root handler does not print lines twice): `RATCHET_LOG_FORMAT` `json` (one object per line) or `text` (`key=value`), `RATCHET_LOG_LEVEL`; unset means JSON and INFO in live mode, text and WARNING in mock mode, so tests and the demo stay quiet. Lines are an event name and fields that are ids, names, numbers and statuses: one `chat` line per chat request (request id, client request id, trace id, client name, task, served_by, route, version, confidence, escalated, audited, latency_ms, wall_ms, cost_usd, status), an `upstream_error` warning per failed model call (role, exception class, status), and every ledger event through the new `Ledger.add_event_listener` hook, its detail scrubbed like a public dashboard's (`access.scrub_detail`). An exception attached to a record shows as its class only. `Ledger.event` calls listeners after the row is committed and ignores a failing listener: a log handler must never fail what wrote it. The night's alert hook (OPS-NIGHT-LEASES-ALERTS) reuses the listener.
- **Prometheus metrics, standard library only.** `ratchet/metrics.py` has `Counter`, `Gauge` and `Histogram` (fixed buckets, cumulative when rendered), one lock per metric, and a process-wide `REGISTRY` rendered in the text format 0.0.4 by `GET /metrics`. The cascade counts each answered request (`ratchet_requests_total` with status 200, the latency histogram, cost and baseline by client, escalations), each model call (`ratchet_upstream_requests_total` by upstream and outcome `ok`, `error`, `timeout` or `circuit_open`, with its latency), each audit by result, each new example by split, and each failure by stage (`ratchet_failures_total`, unsampled, beside the sampled rows) with a failed request's spend (`ratchet_failed_cost_usd_total`); that is all `handle` gains, counter increments, besides the failures rows it is asked to write. The gateway counts each chat request that ended in an error (`served_by="none"`) and each refusal before the cascade by reason. Scrape-time gauges (open breakers, version traffic, today's spend by client) are set from the runtime when `/metrics` is read. Labels stay bounded: a task label is a registered name, `other` or `none`; a client label is a `RATCHET_API_KEYS` name, `none` or `other`, so a caller of `handle` cannot grow the label set.
- **Who reads `/metrics`.** A new access level `metrics`: as `dashboard` (an admin or dashboard key; public with a public dashboard, with client pseudonyms in the labels for an anonymous live reader), and also `RATCHET_METRICS_TOKEN`, a scraper's bearer token that reads nothing else. It is kept as a digest, compared in constant time, must be at least 16 characters and may not also be a key (startup errors).
- **Every version transition has an event.** When a promotion retires the live version, `ReleaseGate._tick_canary` writes a `live_retired` event before the `live` one. Its own kind, not `retired`: v0.4 uses `retired` for candidates replaced at admission, and the pinned reference runs compare release events by kind, so `live_retired` joins the advisory kinds they skip and v0.4's log is unchanged.
- **Trace context, no SDK.** A valid W3C `traceparent` (lower-case hex, version `ff` and all-zero ids refused, version `00` with exactly four fields) is accepted and its trace id logged; `OpenAICompatProvider.complete` adds it to each HTTP attempt with a new span id and the same flags (`obs.upstream_headers`), with a printable `tracestate` of at most 512 characters. A malformed header is ignored; a request without one starts no trace. The OpenTelemetry SDK is deferred: a span per attempt is what a collector needs to join Ratchet to the teacher's traces, and it needs no dependency.

## Alternatives considered

- **`prometheus_client` or the OpenTelemetry SDK.** Either is a new runtime dependency with its own global state and threads; the format is small, and three metric types with fixed buckets cover what the runbook alerts on. A later item can export the same counters through OpenTelemetry.
- **A row for every failed request, 400s included.** A client sending malformed JSON in a loop would turn each request into a write under the ledger's one lock. Validation 400s are counted, and the 401/413/429 rows are throttled per stage.
- **Writing the gateway's rows before the response.** The client would wait for the ledger's lock on an error path. The row is written after the response is sent; a lookup in the same microsecond can miss it, which no client can tell from a slow write.
- **Putting `request_id` inside `error`.** OpenAI's error object has four fields and SDKs build typed exceptions from it; the id goes beside it, like the v0.5 `detail` key, and in the header the SDKs already read.

## Consequences

- One id joins a client's report, the response headers, the error envelope, the ledger rows, the log line and the teacher's trace. An API client can look up its own requests without a dashboard key.
- What failed and what it cost is now in the ledger and in `/ratchet/stats`; savings figures include failed spend. A swallowed student failure counts in `errors.last_hour` although the client got its answer, which is what an operator wants to see.
- Counters live in the process: they reset on restart (Prometheus' `rate()` handles that) and a demo reset keeps them. Several gateway workers each serve their own `/metrics`.
- The `failures` table grows with errors and has no retention yet; the data governance work's retention covers it.
- Live mode logs one JSON line per request at INFO; set `RATCHET_LOG_LEVEL=WARNING` to keep only upstream failures.
- A scrape costs one indexed spend query per API key and table, and reads the stats payload's client list only for a scrubbed read.
