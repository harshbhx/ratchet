# ADR 0041: A generic mock world: every request gets a deterministic answer in mock mode, keyed by what a model sees

- Status: Accepted
- Date: 2026-10-20

## Context

Mock mode is how the demo, the dashboard, the simulator and most of the test suite run Ratchet without keys or GPUs. Its models looked every request up by exact text in two registries, the synthetic support tickets and Scout's research world (`sim.world.lookup`), and raised `KeyError` for anything else, which the gateway turned into a 400 `mock mode only answers demo requests`:

- An SDK user trying the public demo with `hello`, a structured output (`response_format` json_schema) or a tool definition got a 400, so none of the OpenAI-compatibility work (validation, generation parameters, structured outputs, tool calls, `n` choices) could be shown offline on anything but a demo ticket.
- `MockFleet.train` called the same lookup on every stored row, so one example from such a request (stored in a mock gateway that answered it some other way) would have crashed Night School.
- The later compatibility items (structured outputs, tool pass-through, tool distillation, the use-case workloads) need mock models that honour `response_format` and `tools` to test against.

## Decision

- **Registries first, then a generic world** (`sim/generic.py`). `lookup(messages, params=None)` tries the ticket registry, then the research registry, and only then builds a `GenericItem` from the messages and the generation parameters. A demo text never reaches the generic world, so the ticket and research streams, the mock models' draws on them, `make sim`, the pinned reference simulation and the three reference workloads are byte-identical.
- **Four sub-worlds, chosen by what a model is sent:**
  - `tools` when the request offers function tools, `tool_choice` is not `none` and the last message is not a tool result: a call to the catalogue's `lookup_order(order_id)` or `refund(order_id, amount, reason)` with the order number and amount read from the prompt by regex and the reason from keywords; a call to a client's own tool with arguments built from its parameters schema; a plain reply when there is no order number to look up. A forced `tool_choice` is honoured, `required` never gives a plain reply.
  - `schema` for `response_format` json_schema: `instance_from_schema(schema, seed)` builds an instance of the structured-outputs subset (enum and boolean drawn, integer and number within their bounds and `multipleOf`, `mock text` for strings, a date, time, UUID or URI for those formats, 1 or 2 array items within minItems and maxItems, nested objects, local `$ref`, `anyOf`, `oneOf`, `allOf`, `const`). A float `multipleOf` is met as validators test it (the quotient is whole, as jsonschema and ajv check), and a bound past every float gives an exact integer. A `pattern` is not honoured: matching a client's regular expression on the public demo would let one request run an expensive pattern, and the mock's strings are placeholders anyway. It never raises, and one instance has a budget, because the mock gateway is public: depth (`MAX_DEPTH`), at most `MAX_NODES` values and about `MAX_BYTES` (256 KB) of JSON, where a copied enum or const counts every value in it and an enum is drawn from its first `MAX_ENUM` (64) distinct values; each schema part (a `$ref`'s target, an `allOf` merge, an enum's values, a literal's size) is worked out once. Past the budget a part gets its simplest value (its const or first enum value when that is tiny) and an object only its required keys, which may break a minItems or a big const: such a schema has no small instance anyway. A 61 KB schema that `$ref`s a 4,000-value enum from 1,500 properties and recurses made one mock gateway request take 27.6 s before the budget; its instance now builds in milliseconds.
  - `json` for `response_format` json_object: the free-text answer inside `{"answer": ...}`.
  - `text` otherwise: `[mock teacher] ` and a restatement of the prompt (12 words at most), or, after a tool result, of that result (`final`).
- **Labels from sha256 of the request's text**, never from a stream's random generator. The same request gets the same answer in the gateway, the simulator, the trainer and the golden eval, and no existing draw order moves. The labels the mock student can get wrong are the enum, boolean and number fields of a schema instance (enums first, so a slip changes an enum, the confidently wrong case), the tool and refund reason of a call, and the framing of a free-text answer.
- **Templates keyed by what a model sees.** A template is what the mock student's skill grows on. It is the sub-world plus the schema name, the sorted tool names, or a digest of the system prompt; never the task name, because no model, mock or real, is sent it. The mock trainer finds a row's template from its messages and the stored conditions (`examples.params`) the student's allowlist passes (`GenPolicy.student`), as the golden eval and the router send them, so a template is trained exactly where the student will look for it (both default allowlists forward `response_format`; neither forwards `tools` yet, so a row stored with tools trains the free-text template the student is served).
- **Tool calls in the mock before the gateway passes them.** `Completion` gains `tool_calls` (OpenAI's shape, `arguments` a JSON string); only the mock models fill it. The real provider does not read tool calls yet, and the router still refuses a teacher answer that ends in one (502 `tool_calls_unsupported`), so the mock reproduces today's behaviour exactly: with `tools` forwarded to the teacher the call is refused, and by default no model sees the tools and the prose answer is stored. The tool pass-through and tool distillation items change the gateway, not the mock. (Changed by [ADR 0043](0043-tool-calls-teacher-only-by-default.md): the mock teacher's calls now reach the client, and the `tools` workload is answered by the teacher alone and never stored.)
- **`RATCHET_MOCK_STRICT=1`** keeps the old behaviour: the mock teacher and the students the fleet serves raise `KeyError` for anything but a demo request (and for a Scout writer request whose facts they cannot read), so the gateway answers 400. The trainer and the golden eval are never strict: they read rows that were stored already. The `schema` and `tools` demo workloads are generic-world requests, so `POST /ratchet/demo/day` refuses them with a 400 under strict mode before the day starts.
- **Two workloads**, each with its own seeded generator: `schema` (three structured-output tasks, a fourth with nested records from the drift day) and `tools` (look-ups, refunds with a reason and an amount, and questions no tool answers, sent with the catalogue). Both are in `sim.simulate --workload` and `POST /ratchet/demo/day?workload=` (mock only), whose response says `simulation: true`. Their prompts hold no personal data, so redaction never changes them.

## Consequences

- Every request a client can send gets a 200 from the mock gateway, so the SDK, structured outputs and the compatibility features can be shown and tested offline. Tests that relied on the mock's 400 now set `RATCHET_MOCK_STRICT=1` or expect the answer.
- The `tools` workload shows a known gap honestly until the tool pass-through item lands: the default allowlists keep `tools` from both models, so both answer in prose and that prose is stored and learned (simulation). (Changed by [ADR 0043](0043-tool-calls-teacher-only-by-default.md): the teacher now answers every tool request alone with its calls and nothing is stored, so the workload never trains the student.) The schema workload is learned like tickets (simulation, mock models).
- Free-text answers are compared as whole texts under the default task, so a student that "knows" a free-text request repeats the teacher's wording, prefix included. That is what distillation does; it is still a mock.
- Schema labels are seeded from the text, not read from it: the mock teacher may rate a glowing review `negative`. The mock teacher is right by definition; these numbers say how the loop behaves, never how good a model is.

## Alternatives

- **Register generic requests as they arrive**, as the ticket stream registers its texts. Any client could then grow a registry in the shared demo without bound, and the trainer would still crash on a row from before a restart.
- **Key templates by the task name.** The spec suggested it, but the providers never receive the task, so a student could not find the template it was trained on; the system prompt stands in for the task.
- **Return tool calls through the gateway now.** That is the tool pass-through item's decision (routing, storage, streaming, redaction of arguments), not the mock's.
- **Answer unknown requests with a fixed string.** Cheap, but a fixed answer cannot be wrong, so nothing could learn or be audited, and no schema or tool call could be shown.
