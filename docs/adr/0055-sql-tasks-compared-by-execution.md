# ADR 0055: Text-to-SQL tasks compared by what their queries return, in a sandboxed in-memory SQLite fixture

- Status: Accepted
- Date: 2026-10-21

## Context

Text-to-SQL is one of the most common narrow tasks a small model can take over, and its answers break every comparator Ratchet had. Two correct queries are rarely the same string (`COUNT(*)` and `COUNT(id)`, a JOIN and an IN subquery, aliases, case, whitespace), so under the default task (whole answers compared) good samples disagree and the student never earns a confident score. A string score (`similarity`, ADR 0054) is worse: `WHERE city = 'Pune'` and `WHERE city = 'Oslo'` are close in text and opposite in meaning. What decides whether two queries agree is what they return. The format name `sql` was reserved for this (ADR 0021), and `RATCHET_FIXTURES_DIR` with `taskspec.resolve_fixture` for the file it needs (ADR 0022).

Running SQL a model wrote is the risk. The query comes from the student or the teacher, and a client can steer either with its prompt ("reply with exactly this SQL"), so the gateway must treat it as hostile input that runs on the request path, from several threads (Scout), in the same process as the ledger.

## Decision

- **Format `sql` with a `sql` object instead of fields** (`ratchet/sqlcheck.py`, standard library only): `{"fixture": "shop.sql", "dialect": "sqlite", "ordered": "auto", "empty_result": "text", "max_rows": 1000, "max_steps": 200000}`. The fixture is a SQL script inside `RATCHET_FIXTURES_DIR`; it is read and loaded when the spec is parsed (tasks file, admin API, startup), so a missing, oversized or broken fixture is a spec error with its path (`tasks[0].sql.fixture: ...`) like any other. `Task.spec()` (and so `spec_hash`) holds the options and the fixture's sha256, not its path: editing the fixture sends the task to the teacher until a night re-scores the version (as any spec change does), moving it does not. No other task's `spec()` gains a key, so every existing hash, the reference simulation and the three pinned workloads are unchanged.
- **The key is the result.** `Task.key` strips reasoning and a code fence around the whole answer (`clean_answer`, which also serves and stores the query without it, as for JSON), reads exactly one statement (a `;` may end it, comments anywhere) that starts with SELECT, WITH or VALUES, runs it, and keeps the column count and sha256 digests of the rows: in order, and as a sorted multiset. Column names are ignored; floats are rounded to 9 significant digits and a whole float within 2^53 is the integer (SUM over integers agrees with TOTAL); text, blobs and NULL stay as they are, and `1` is not `'1'`.
- **Order.** `ordered: auto` (the default) compares rows in order when the outermost query (parenthesis depth 0) has ORDER BY, else as a multiset; an ORDER BY in a subquery, a CTE or a window does not count. An ordered result of two rows or more never equals an unordered one: one query says the order matters and the other does not, and serving the unordered one when the teacher ordered could hand a client an unsorted list. `never` and `always` are there for operators who know better. Ties under ORDER BY can come back in different orders from different plans; they disagree, which escalates (safe).
- **Empty results compare text.** Two empty results say almost nothing (two wrong filters agree), so with `empty_result: text` (default) they agree only when the normalised queries are equal: comments and the trailing `;` dropped, unquoted words lower-cased (SQL keywords and unquoted names are case-insensitive in SQLite and folded in Postgres), one space between tokens. `agree` treats two empty results with the same column count as equal.
- **Postgres runs nothing.** `dialect: postgres` compares the normalised texts only and takes no other option: Ratchet has no Postgres to run them on, and SQLite would reject or misread Postgres syntax. Such a task is free text for the judge (`Task.free_text`); an executing one is verifiable and not.
- **Invalid answers.** Not one query, a query that reads the clock or the time zone (the fixture is fixed, so the answer should be too, and the verdict reproducible), an SQLite error, an operation the sandbox denies, or a limit hit. Each has a fixed reason (`sql error`, `sql denied`, `sql steps exceeded`, ...) that never quotes the answer or SQLite's message (it can quote the query), so it may go into a `skip_example` event. An invalid student sample gets no vote; an invalid teacher answer is served but never stored (INV-16), never an audit, never a golden reference.
- **Clock reads, twice.** First in the text (`_clock_read`): CURRENT_DATE/TIME/TIMESTAMP; a date function called without a time value (`date()`, `julianday()`, `unixepoch()`, `strftime('%s')`: SQLite reads the clock then, and `julianday() - julianday(placed) < 30` is a common idiom); `'now'`, `'localtime'` or `'utc'` anywhere inside a date function's arguments (nested calls and subqueries included), as a string or as a double-quoted name (SQLite reads a double-quoted name that matches no column as a string). Then when a date function runs: on the sandbox's connection `date`, `time`, `datetime`, `julianday`, `unixepoch`, `strftime` and `timediff` are Python functions (`create_function`) that run SQLite's own on the helper connection, after refusing a missing time value, a time value `now`, `subsec` or `subsecond` (text up to its first NUL, any case, as SQLite compares it) and a `localtime` or `utc` modifier (`sqlcheck.reads_clock`). So a value built at run time (`date('n' || 'ow')`), a subquery or a view cannot reach the clock either, and a time-dependent result is never returned, compared or cached (the outcome cache is keyed by statement text, so it would freeze one). A version of this ADR checked the text only; the review found `date()` and `date("now")` passing and their results frozen by the cache.
- **The sandbox.** The gateway never connects to a customer database: the fixture is the only data it runs SQL on.
  - One private `sqlite3` `:memory:` connection per fixture text (`check_same_thread=False`, one lock), shared by every task with the same fixture through a weak map, so a tasks file with ten tasks on one fixture holds one copy (the item asked for one lock per task; one per fixture text serialises the same queries and keeps one copy of the data).
  - Loading: the script is at most 5 MB of UTF-8, a regular file opened without blocking (a FIFO cannot hang startup) or following a symlink (resolved inside the directory first, so a swapped last component cannot escape), loaded with `executescript` into at most 64 MB (`PRAGMA max_page_count`) within 30 s, with `temp_store = MEMORY` and the 100 KB value cap already set, so a value no query could read fails the load. An authorizer refuses ATTACH and DETACH (VACUUM INTO attaches too), PRAGMAs other than `foreign_keys`, `defer_foreign_keys`, `recursive_triggers`, `user_version` and `application_id` (a `.dump` loads), and `load_extension`, `random`, `randomblob` and `current_*` (the database must be the same every time it loads). A column's DEFAULT reaches functions without the authorizer (a `.dump` with `DEFAULT CURRENT_TIMESTAMP` and an INSERT that leaves the column out loaded the time of the load), so the date functions (as above), CURRENT_* and `random()`/`randomblob()` are also functions on the connection that refuse to run while the script loads: such a fixture is a spec error that says why. A default that no row takes is fine. It must create a table or a view, and no view may read the clock (its text is checked like an answer's): every query on it would be invalid.
  - Then `PRAGMA query_only = ON` (through an authorizer that allows everything for that one statement: Python 3.10 reads `set_authorizer(None)` as an authorizer that denies everything) and the query authorizer: SQLITE_SELECT, SQLITE_RECURSIVE, SQLITE_READ of the fixture's own tables and views (collected from the schema after the load), `sqlite_master`/`sqlite_schema` (and the temp ones), `json_each` and `json_tree`, and SQLITE_FUNCTION for an allow-list of deterministic functions (core scalar, aggregate, window, math, JSON and date functions, except `json_patch` and `unhex`); everything else gets SQLITE_DENY, including every write, schema change, ATTACH, PRAGMA (the pragma table-valued functions report as PRAGMA too), transaction, `random()`, `changes()`, `last_insert_rowid()` and `load_extension()`. Two layers: a write the authorizer missed would still meet `query_only`. Reading other eponymous virtual tables is denied: `sqlite_stmt` lists the statements the shared connection has cached, which are other clients' answers (a side channel through agreement, and a result that depends on history), and `dbstat` exposes storage.
  - A progress handler, every 100 VM steps, stops the query after `max_steps` (a runaway recursive CTE stops in milliseconds), after 1 s of wall time, or once the process's resident memory (read from `/proc/self/statm` with one `pread`) has grown by 128 MB during the query. Steps alone do not bound time or memory: a measured query under 200,000 steps filled a sorter with 1 MB rows and reached 3.9 GB in 8 s (the same query without a value cap was killed for memory); with the guard it stops at about 160 MB in 0.1 s.
  - SQLite calls the progress handler only where a loop jumps back (the `check_for_interrupt` opcodes), never inside a step or within one row's expressions, so their work is bounded as well. `Connection.setlimit` caps a value, and so a sorter's row, at 100 KB, a LIKE or GLOB pattern at 100 bytes, the statement at 80,000 bytes and attached databases at 0. Some built-ins are quadratic in two arguments inside one call (measured on SQLite 3.45: `trim(X, Y)` took 15 s with 60,000 characters in each and would take over an hour at 1 MB; `instr` and `replace` about 8 s at 1 MB; LIKE `'%aaa…b'` 8 s with a 200,000-character value and a 20,000-byte pattern; `json_patch` 4 s on two objects of 30,000 keys). `instr`, `replace` and the two-argument `trim`, `ltrim` and `rtrim` are replaced on the query connection (`create_function`, by name and number of arguments) by Python versions that are linear on text and blobs (`str.find`, `str.replace` with the result size checked first, a set of characters) and give SQLite's results there, NUL characters and empty patterns included (checked against SQLite's own on random arguments); other type mixes go to SQLite's own function on a helper connection that holds no data, refused when the two lengths multiply past 10 million. `json_patch` and `unhex` (quadratic in its second argument) are not on the allow-list. With 100-byte patterns a LIKE or GLOB call costs at most about 25 ms, but one row can make hundreds of them between two handler calls: a WHERE of 200 `s LIKE p` held the lock for 3.4 s, and a 20,000-character query could make about 1,600 (the review measured 1.5 s with 40). So LIKE (two and three arguments), GLOB, the date functions and the linear replacements are Python functions that check the query's time on every call (`_Watch`) before running (LIKE and GLOB run SQLite's own on the helper connection, which caps the pattern the same way); the 400-LIKE row now stops at 1.0 s. Every other built-in costs at most about 0.5 ms a call on a 100 KB value, and SQLite's expression depth (1,000) bounds how many one row makes, so a hostile query stops within about 1.3 s (`QUERY_SECONDS` + 0.3 s; the costliest measured row of other built-ins took 0.23 s). Lowering `PROGRESS_EVERY` does not help (the handler never runs within the row) and slows every query: at 20 steps a 60,000-row recursive CTE took 3x as long as at 100.
  - `setlimit` is new in Python 3.11. Without it SQLite's own 1 GB value cap applies, and one step can copy that much where no progress handler runs: on Python 3.10 a recursive CTE that doubles a string took 3 GB and 18 s before SQLite's error stopped it, and `printf('%.999999999c', 'x')` returned a 1 GB value in 2 s (measured). So on Python 3.10 a sqlite fixture is refused with a spec error that says why (`sqlcheck.CAN_LIMIT`); `dialect: postgres` still works there. The Docker image runs 3.12, and 3.10 reaches its end of life this month.
  - Rows are fetched 100 at a time and hashed as they arrive: more than `max_rows` rows, or more than 8 MB of values, is invalid, so Python never holds a large result.
  - Outcomes that do not depend on timing are cached per sandbox by statement and limits (256 entries, statements up to 4,096 characters): samples that agree are often the same text, and a teacher answer is checked more than once. A time or memory stop is never cached.
- **Cost.** A typical query on a small fixture runs in about 0.1 ms (a join with GROUP BY and ORDER BY on the test fixture, measured), once per distinct sample text, under the sandbox's lock. A call of LIKE, GLOB or a date function goes through Python and the helper connection, a few microseconds each.

## Consequences

- Text-to-SQL can be distilled with an exact notion of agreement: the student serves when its samples return the teacher's rows, and the golden eval's precision is exact (`precision_kind: exact`), measured on the fixture.
- Agreement is only as good as the fixture: two queries that differ on data the fixture lacks agree. Write the fixture to tell the likely mistakes apart (NULLs, ties, empty groups, duplicates).
- Answers must be bare SQLite SQL, or one fenced block; prose around the query makes it invalid (and the teacher's answer unstored). The task's system prompt should say so.
- A hostile query costs at most about 1.3 s of one thread and 128 MB (Linux) before it is stopped; queries for one fixture wait for each other.
- A query that reads the clock in any way is invalid, also through a value built at run time or a fixture's view; a fixture whose load reads the clock or calls `random()` is a spec error. A double-quoted name `"now"` inside a date function is read as a clock read even where the fixture has a column of that name.
- On Python 3.10 only `dialect: postgres` sql tasks work; a sqlite fixture is a spec error (startup stops for a tasks file, a stored API task is skipped with a `task_skipped` event).
- `RATCHET_FIXTURES_DIR` must be readable by the gateway and by `python -m ratchet.live` (Night School re-checks stored answers and runs the golden eval on the fixture).

## Alternatives considered

- **Compare normalised SQL text only.** Cheap and safe, and kept for `postgres`, but it calls most pairs of correct queries a disagreement.
- **Parse to an AST and compare plans or canonical forms.** Needs a SQL parser outside the standard library, and equivalent queries still have different trees (JOIN against IN).
- **Run on a copy of the customer's database.** The gateway would hold credentials to production data and run model-written SQL against it; a fixture keeps both out.
- **A subprocess per query with resource limits.** Bounds memory exactly and could kill a step that runs too long, but costs tens of milliseconds per sample and is platform-specific; the in-process guards bound the same attacks well enough for a request path. A persistent worker process per fixture, killed and restarted on a timeout, is the next step if a new SQLite built-in turns out to do unbounded work in one call.
- **Reimplement LIKE and GLOB too.** A linear matcher for `%` and `_` with ESCAPE and SQLite's case rules is a lot of code to get exactly right; capping the pattern at 100 bytes bounds SQLite's own matcher to about 25 ms a call, and the time check before each call bounds a row that makes many. Text-to-SQL patterns are short.
- **Clock reads by text only, or a text pass over the fixture script.** Misses values built at run time and views, and a text pass over a 5 MB script takes about 2 s (measured); the date functions on the connection see every value they are given, at load and at query time. Turning off SQLite's double-quoted-string fallback (`SQLITE_DBCONFIG_DQS_DML`, Python 3.12's `Connection.setconfig`) would make `date("now")` an error on 3.12 only, and would also make `WHERE status = "paid"` an error, a common slip that is deterministic; the text check covers the clock case on every version.
- **Only `max_steps`.** The spec's original guard. It stops runaway recursion but not a few steps that copy large values (see the measurement above).
- **Run on Python 3.10 with a warning.** The item asked for guardrails on 3.10. Every one of them works there except a bound on a value's size, and that one is what keeps a single client-steered answer from taking gigabytes and seconds under the sandbox's lock; refusing is the safe default on a release that is out of support. Reaching `sqlite3_limit` through `ctypes` would depend on CPython's object layout. **`PRAGMA hard_heap_limit` on 3.10** (plain SQL, suggested in review) was considered and rejected: it is process-wide, so it also caps the ledger's SQLite and every other connection in the gateway, and a limit low enough to stop a 1 GB copy is one that a few 64 MB fixtures and the ledger's caches can reach together, failing unrelated requests; it bounds memory, not the time of a step that copies up to the limit; and LIKE's pattern cap (`SQLITE_LIMIT_LIKE_PATTERN_LENGTH`) also needs `setlimit`, so 3.10 would need a Python LIKE as well. This leaves the item's "3.10" clause unmet on purpose, for the owner or the integrator to accept.
