# ADR 0050: The other OpenAI endpoints: an embeddings pass-through, completions and stateless responses on the chat path, typed 404s

- Status: Accepted
- Date: 2026-10-21

## Context

Ratchet is meant to be a drop-in base URL: point an OpenAI client at `/v1` and nothing else changes. But a real client calls more than `/v1/chat/completions`. A retrieval app embeds its documents and queries through the same base URL (`/v1/embeddings`); older tools and evaluation harnesses call the legacy `/v1/completions`; newer SDK code and agent frameworks call `/v1/responses`; guardrail libraries call `/v1/moderations`. Each of these was a 404 `unknown_url`, so switching the base URL broke the application in its first minute, and a team would have to split its traffic across two base URLs to try Ratchet at all.

These endpoints differ in what Ratchet can do with them. Embeddings are vectors, not text a student can learn to write, and a vector from one model cannot be compared with a vector from another. Completions and responses are chat requests in another shape. Moderations needs a moderation model Ratchet does not have, and much of the Responses API (stored responses, conversations, background runs, built-in tools) needs state on the server.

## Decision

- **`/v1/embeddings` is a pass-through to one configured model** (`RATCHET_EMBEDDINGS_MODEL` at `RATCHET_EMBEDDINGS_BASE`; the teacher's Token Factory endpoint and key by default, `off` to turn it off). The Token Factory key goes only to the teacher's own endpoint: another base gets `RATCHET_EMBEDDINGS_KEY`, or no key at all, so pointing embeddings at another provider (or a local server) can never send it there. No cascade and no distillation: nothing of the request is stored. The client's `model` never selects the upstream model, for the same reason the chat path's never does (ADR 0048): a client string must not choose what the gateway calls. Under `RATCHET_MODEL_POLICY=strict` only `ratchet` and the configured id are served, since an index built with `text-embedding-3-small` silently filled with another model's vectors is worse than a 404; `/v1/models` lists the configured id so a strict client can find it. The upstream is always asked for floats (no `encoding_format`, which some servers do not accept) and the gateway encodes base64 itself, which the OpenAI SDKs ask for by default. The upstream's answer is checked (one vector per input, found by its index, all one length, finite, within float32) before a client gets it. Calls get the teacher's timeouts and retries and no breaker; failures map by cause like a teacher's (ADR 0014) with `upstream_*` codes. Mock mode embeds locally: a unit vector per input seeded from SHA-256 of its text, so the same input always gets the same vector; `dimensions` keeps a prefix and renormalises, as OpenAI's shortened embeddings do; one request may ask the shared demo for at most 2^20 floats.
- **An embeddings call is logged and counted like any request**: one row, task `embeddings`, served_by `upstream`, route `passthrough` (the gateway's route, not the router's), `stored` 0, priced at the configured model's input price (`EMBEDDING_PRICES`, kept apart from `DEFAULT_PRICES` because those models are licensed teachers, judges and students; a model without a price is priced as the teacher, an overstatement rather than a hidden cost). Its all-teacher baseline is its own cost, so no savings figure moves, and its cost sits in the teacher (hosted spend) column so the cost report's split still adds up. It counts against the key's daily quota. The name `embeddings` is reserved (`tasks.RESERVED_NAMES`): a chat request that names it (header, metadata, `model`, Azure deployment) is a 400 `reserved_task` before the quota, a spec or model alias that names it is refused, and `/v1/models` and `/ratchet/tasks` never offer it, so the `embeddings` row in the stats is only ever pass-through requests and never mixes with a chat task's. Embeddings rows count in the request totals and the per-day student share, as a pinned task's teacher-only requests do: both are traffic the student never answers, told apart in the per-task stats.
- **`/v1/completions` and `/v1/responses` run the chat path.** Each becomes a `ChatRequest` (`openai_compat.validate_completion_request`, `validate_responses_request`) and goes through `gateway._serve`, the part of the chat handler after validation: the model check, task resolution and admission, the quota, the cascade and the `ratchet` block. So they are answered, logged, audited and stored exactly as the chat request they become, and whatever later items add to the chat path (budgets, idempotency, tool calls) reaches them without another change. A completion's prompt becomes one user message, so it is stored as that chat request's example. A batch of prompts runs one request per prompt, each logged and counted; the quota is checked for the whole batch before the first prompt runs, so a batch never stops halfway for want of quota.
- **Refuse what would change the answer, accept what does not.** A non-empty `suffix`, `echo: true` and a `best_of` other than 1 or `n` are a 400 `unsupported_parameter`; token-array prompts a 400 `unsupported_value`. On `/v1/responses`, `previous_response_id`, `conversation`, a stored `prompt`, `background: true`, `stream: true` and built-in tools are a 400 `unsupported_parameter`; `include`, `truncation`, `store` and caching hints are accepted and do nothing; errors name the Responses field (`max_output_tokens`, `text.format.name`). Function tools and `function_call` / `function_call_output` items map to the chat tool fields, so a stateless tool loop works and follows the chat path's tool rules: consecutive calls become one assistant message, joined to the assistant message item right before them (a response's `output` lists its text and then its calls), and `reasoning` items are dropped without splitting them, so a loop sent back as input is the chat conversation it would be and is stored as that request. A choice's tool calls become `function_call` items once the chat path returns them. Legacy `logprobs: k` returns the legacy shape from the chat path's token logprobs.
- **Typed 404s.** `/v1/moderations` and the stored-response routes (retrieve, delete, cancel, input items) answer 404 `unsupported_endpoint` after the key check, with a message that says why and links the endpoint table in docs/API.md; any other `/v1/*` path stays `unknown_url`.

## Consequences

- An application that uses chat, embeddings, legacy completions and stateless responses through one base URL works against Ratchet unchanged; its chat-shaped traffic is distilled, its embeddings pass through at the provider's price.
- Embeddings rows count in `/ratchet/stats` request totals and per-day figures (the student share is over all requests, embeddings included, as pinned tasks are) and show as an `embeddings` row in `tasks` whose routes are all `passthrough`. The release gate never sees them: its queries filter on student or shadow versions. A heavy embeddings client lowers the headline student share; the per-task rows say why.
- A chat task named `embeddings` (in a tasks file, the admin API or a stored API task) no longer loads; it has to be renamed.
- A client that relied on `/v1/completions` defaulting to 16 output tokens gets the gateway's caps instead; a client that needs streamed response events, server-side conversations or OpenAI's built-in tools gets a 400 that names the field, and keeps using `/v1/chat/completions` for those.
- A failed prompt in a completions batch fails the request; the prompts answered before it stay logged and billed, as separate chat requests would.
- The embeddings model and its price are unverified until `scripts/day1_check.py` passes with a real key (INV-9); the check lists and calls it.
- `gateway._complete` now validates and hands over to `_serve` and `_chat_response`; the lines did not change order, so other items' edits to the chat handler land in `_serve` and reach all three endpoints.
