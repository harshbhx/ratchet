# ADR 0049: Risk-aware routing: eligibility, escalation rules on the student's answer, a critical-class miss-rate gate, and a per-task audit rate

- Status: Accepted
- Date: 2026-10-21

## Context

The cascade treats every answer of a task alike: a confident student serves, an unsure one escalates. Real tasks are not alike inside. A moderation task's `flagged: true` costs far more when wrong than `flagged: false`; a support task's `priority: urgent` must not be missed; a request longer than the student was trained on (`train.py --max-seq 2048`) or with an image the student cannot read is one it should never see. Operators had no way to say so short of pinning the whole task to the teacher, which gives up all of its savings. The task spec has had a `routing` block since the task registry (ADR 0022), accepted as free JSON and read by nothing, and `policy.audit_rate` was reserved for a later release.

The release gate also had nothing to say about which mistakes a candidate makes: a task at 97% precision can still miss most of a rare class whose misses are the expensive ones, because precision over all served answers hides it.

## Decision

- **A routing block, parsed once** (`ratchet/routing.py`, standard library only). `Task.__post_init__` parses `routing` into a frozen `Routing` (`Task.routing_rules`) and `taskspec` reports every problem with its path, so a bad block stops startup or gets a 422 from the admin API. A condition (`{field, equals | in}`) must name a declared field of a scalar type, and its values must be values that field accepts; they are normalised by the field when the task is defined, so on the request path a rule compares normalised keys with the field's own comparator (a label alias, a number's tolerance). The block is part of the spec hash, so changing it sends the task to the teacher until a night re-scores the version (FR-2.15).
- **Eligibility, before a version is picked.** `student_max_input_tokens` (characters of the message text / 4, the way the gateway's input limit counts them and `approx_tokens` estimates) and `student_content_types` (`text` only; other types reserved until a student reads them). An ineligible request goes to the teacher through `Ratchet._ineligible`, route `ineligible:input_tokens` or `ineligible:content_type`: no canary draw, no student call, no audit, no shadow, no degraded answer, and not counted as an escalation (the student never had it). Its answer is stored only for an over-length request with `store_ineligible` (default false, because train.py cuts every example at `--max-seq`), and then through `_store_example` with all its rules; a request with a part the student cannot read is never stored. The gateway's multimodal path (`RATCHET_TEACHER_MODALITIES`), which went to `teacher_only` and was logged as `pinned`, now goes through `handle` and this check, so its route says why. The golden eval leaves such rows out (`excluded_ineligible`), since production never shows them to the student.
- **`escalate_when`, after the threshold.** Rules run in order on the key `confidence.score` already computed for the answer a confident student would serve (`Scored.key`, so no second parse): `action: teacher` sends an answer in the class to the teacher, `min_confidence: x` does unless the confidence is at least `x`. The first rule that holds names the route (`rule:<i>`). The teacher's answer is stored like any escalation's. An answer a rule holds for never stands in for an unavailable teacher (degraded mode), also when the student was below the threshold, and a shadow applies the same rules before it counts as serving. The golden eval applies them too: an answer a rule sends to the teacher neither calibrates the task's threshold nor counts as served in the precision and coverage the gate checks (the task's record and the pooled numbers), so a task cannot pass its floor on answers it never serves, and a rule that catches most answers shows the low coverage that keeps a version from waiting in shadow or canary forever (INV-5). A task without rules is calibrated and measured exactly as before.
- **Critical classes, measured and gated.** `critical: [{field, equals | in, max_miss_rate}]`. The golden eval records per class, on the task's held-out rows, `n` (rows whose teacher reference is in the class) and `misses` (those whose answer the student would serve, at the task's threshold and past its rules, while it is not in the class), with the miss rate and its 95% Wilson upper bound (`eval['tasks'][t]['critical']`). Misses are counted at the threshold the record stores, the one the router applies, not at the unrounded calibrated value. The gate (`ReleaseGate.critical_failure`, first in `task_failures`) fails the task unless every class has at least `RATCHET_MIN_TASK_TEST_N` (10) such rows and an upper bound at most its `max_miss_rate`; a failing task is disabled or the version rejected per `RATCHET_TASK_MODE`, like any task failure (FR-14.1). A night's re-score of the live version (champion re-check, or a skip night's re-score after a spec change) applies the same check in the same eval write (`ReleaseGate.critical_holds` in `orchestrate.rescore`), so a class added to a live task, or more misses on a growing golden set, takes the task off that version, and the version never serves it on numbers no gate looked at. The router serves such a task from the student only on a version whose record carries the measurements (`calibration.critical_measured`); without one (no golden rows yet, or scored before the classes existed) it is held back (route `task_disabled`, no student call), and the hosted untuned fallback model never answers it, nor is sampled for it (`Ratchet._held_back` asks the resolver). A task with critical classes gets its record also with `RATCHET_PER_TASK_CALIBRATION=0`, because the gate and the router read it; since the records then cover only some tasks, the eval also writes `other_tasks` (the other tasks' held-out rows and how many the pooled threshold serves), which the gate adds when it checks the coverage left after disabling a task, so disabling the critical task leaves the version the coverage of its other tasks rather than none.
- **Per-task audit rate** in the existing `policy.audit_rate` (`Ratchet.audit_rate`), not a second key in the routing block: `policy` already holds the task's other release numbers (`target_precision`, `min_precision`) and reserved this one. One random draw per served answer either way, so a task without its own rate is audited on exactly the same requests as before.
- **Route values** are open families (`router.RULE_ROUTE`, `router.INELIGIBLE_ROUTE`, `router.known_route`); `ROUTES` keeps the fixed names. `stats_by_task.routes` shows them as they are logged.

## Consequences

- An operator can keep a task distilled and still send its costly positive predictions, its long prompts and its images to the teacher, at the price of a few microseconds per request (one pass over the messages, comparisons on a key already computed).
- Rules see the answer the student gives, never the one it should have given, so they cannot catch a costly miss (a `flagged` post the student calls clean). That is the critical gate's and the audits' job, and the docs say so. A strict `max_miss_rate` needs many golden rows in the class (with no misses: 35 rows for 10%, 73 for 5%, 381 for 1%), so such a task stays on the teacher longer; that is the evidence the limit asks for.
- The gate's burden of proof is on the candidate: fewer than `RATCHET_MIN_TASK_TEST_N` rows in a class fail it. The spec this was built from passed a class below 10 rows unchecked, which would let 9 rows pass where 10 fail; failing both is the consistent rule, and it only ever costs coverage.
- A stored API task whose `routing` held free JSON from the registry's first release no longer parses; startup skips it with a message (`taskspec.install`) and the admin API can fix it. Nothing read that block before, and the built-in tasks have none.
- With no routing block and no `policy.audit_rate`, nothing moves: the random draws, routes, stored examples, evals and events are those of before, and the pinned reference simulation and the three reference workloads are byte-identical.
- The anytime-valid canary audit rate (`RATCHET_CANARY_AUDIT_RATE`, reserved for FR-16.1) will have to say how it combines with a task's `policy.audit_rate`; until it is built, the task's rate applies to every version.
- With per-task audit rates, the version-level release statistics (the canary's rollback and promotion rule, the live alert: `Ledger.version_live_quality`) pool audited answers without weights, so each task counts by its volume times its audit rate, and a task audited at 0 is not in them at all. That is a choice of emphasis an operator makes by setting the rate, not an unbiased estimate of the precision of all served answers; the per-task alerts are per task, so unaffected. A replay or estimator that weights audited rows by their labelling probability (the ledger time machine's `label_p`, FR-16.5) must take the task's rate, `Ratchet.audit_rate(task)`, not `Settings.audit_rate`.
- The golden eval checks eligibility on the stored prompt, which was redacted (INV-12): a placeholder is shorter than what it replaced, so a request stored with `store_ineligible` just over `student_max_input_tokens` can come back just under it and be scored. Storing the decision with the example would need a column for one edge case; the approximation touches only rows near the limit, and only with `store_ineligible`.

## Alternatives considered

- **Rules on the request (keywords, regexes on the prompt).** Cheap to check before sampling, but a pattern over free text is easy to evade and slow to get right, and it duplicates what the task's fields already define. Rules on the parsed answer use the comparators the task already has.
- **`audit_rate` inside `routing`, as first proposed.** Two places for one task's release numbers would invite conflicting values; `policy.audit_rate` was already reserved for it. A routing block naming `audit_rate` is refused with a hint.
- **Checking the miss rate in the router.** The router would need the release policy and would repeat the gate's decision on every request; the gate writes its decision (`disabled`) once, and the router only checks that a decision was possible (`critical_measured`).
- **Passing a class with fewer than 10 rows.** Rejected above: more evidence would then fail where less passes.
