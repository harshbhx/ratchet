# ADR 0071: Idempotency keys, and retries that never count as repeats

- Status: Accepted
- Date: 2026-10-21

## Context

OpenAI's SDKs retry a request twice by default after a timeout, a dropped connection, a 408, 409, 429 or 5xx, and many clients wrap their calls in retry loops of their own. A code reading found what a retry did at the gateway:

- Every retry ran the whole cascade again: the student's samples, and for a request the student cannot answer, a second teacher call. A client whose first attempt timed out on its side while the gateway was still working paid twice for one answer.
- `Ledger.add_example` added one to a duplicate's `seen` on every repeat. Three retries of one escalated request reached `FREQUENT` (3), and `dataset.rows` then moved a golden example into training (ADR 0007). The frequent-request rule exists for requests that real traffic keeps asking; retries counted as traffic defeat the point of holding the golden set out (INV-3), and a client that retries hard could drain it.
- Nothing recorded whether a request was a retry.

## Decision

- **An `Idempotency-Key` header makes a chat request idempotent per API key.** `ratchet/idem.py`'s `IdemCache` keys answers by (API key name or '', the client's key), never the API key (INV-13). The value is the sha256 of the parsed body with sorted keys plus the `X-Ratchet-Task` header (so a client that serialises its retry again matches; headers that differ between attempts do not count), and the state: running (a `threading.Event`) or finished (the answer as sent). The first request with a key runs the cascade; the same key and body while it runs waits for it, at most `RATCHET_TEACHER_DEADLINE_S` and at most four such requests at once (`MAX_WAITERS_PER_KEY`: a waiter holds a worker thread and uses no quota, so copies of one request must not hold the thread pool), and gets its answer; once it finished, the answer comes back at once with `Idempotent-Replayed: true` and the same body (the same completion id), with no cascade, no ledger row, no quota use and no rate-limit headers. The same key with another body is a 400 `idempotency_key_reused` with `X-Should-Retry: false`: not a 409, because the SDKs retry a 409 and no retry can fix a reused key. A wait that runs out, or a fifth waiter, is a 409 `idempotency_key_in_use` with `Retry-After: 1`, which is the retry the client should make. A key that is not 1 to 255 printable ASCII characters is a 400 `invalid_idempotency_key`.
- **Only successful answers are kept.** A request that failed (a teacher outage, the quota, a validation error) releases its key, and the requests waiting for it wake and one of them runs: a client's retry after an error is meant to run again. An error kept for ten minutes would turn one teacher blip into ten minutes of errors.
- **The claim comes after the body parses and before validation and the quota.** Bad JSON never claims a key; a replay of an answered request is served even after the key's daily quota is used up (it costs nothing), and is never refused by a rule that changed since.
- **Bounded, in memory, per process.** At most `RATCHET_IDEMPOTENCY_CACHE` (10,000) answers and 64 MiB (each answer counted as its body plus `ENTRY_OVERHEAD`, 2 KiB, for the entry, its `Event`, headers and log fields, about 1.9 KB measured; without it the budget would bound only the bodies, and 1,000,000 tiny answers would hold about 2 GB), the least recently used finished answer dropped first and a running entry never; each kept `RATCHET_IDEMPOTENCY_TTL_S` (600 s) after it finished, on the runtime's clock; expired answers swept at most once per half TTL. Answers hold request-derived text, so they are never written to the ledger or to disk (INV-12). `RATCHET_IDEMPOTENCY_CACHE=0` turns the header off.
- **Streams are kept as their events.** The cascade decides before the first chunk (FR-1.6), so for a request with a key the gateway renders every Server-Sent Event first (`BufferedStream`) and sends them from an async iterator; the same events are kept and replayed. A stream without a key is sent as before. A response that is not a 200 JSON body or a buffered stream is not kept (the key is released), so a stream produced while it is sent (real teacher streaming) can be added later without a wrong replay: its duplicates run again.
- **A retry never counts as a repeat.** `Ledger.add_example(..., count_seen: bool = True, sender: str | None = None)`. The router passes `count_seen=False` when `RequestMeta.retry_count` (the gateway's reading of `x-stainless-retry-count`, which OpenAI's and other Stainless-built SDKs send on every attempt) is above 0, and the sender: the API key's name ('' with keys off) of the request the gateway is serving, or None outside one. With a sender, the ledger's `SeenWindow` (RATCHET_SEEN_DEDUP_S) counts the same (example, sender) at most once per window: a client without an SDK retrying a few times in a row counts once. The window is checked and the row written under the ledger's lock, so two concurrent retries cannot both count; a new example starts its pair's window; a skipped repeat does not restart it; at most 10,000 pairs are remembered. `requests.retry_count` (new column, `SCHEMA` and `MIGRATIONS`, default 0) records the attempt number.
- **The window is for clients; mock mode keeps it off by default.** Internal callers (Scout's agents, the simulator, the mock warm-up) pass no gateway request, so their repeats always count: they are traffic by construction. Unset, RATCHET_SEEN_DEDUP_S is 300 s in live mode and 0 in mock mode, as `RATCHET_TICK_INTERVAL_S` is: the mock demo's repeated synthetic tickets are traffic, and the contract tests and the reference runs keep v0.4's counts. The demo VM's `.env.vm.example` sets 300 s, so the public mock demo, which takes requests from anyone, holds a client's quick repeats to the live rule. The SDK's retry count is honoured in both modes.

## Alternatives considered

- **Cache errors too, as Stripe does.** A retry exists to get past an error; replaying a teacher 502 for ten minutes would make every client's retries useless. Validation errors cost nothing to recompute.
- **A 409 for a reused key.** The SDKs retry 409s with backoff, so a client bug would turn into three refused requests and a delay; a 400 with `X-Should-Retry: false` fails at once with a message that says what to fix.
- **Answer a duplicate that arrives while the first runs with an immediate 409, as Stripe does.** The client then has to retry and wait anyway; waiting on the worker thread the request already holds returns the answer as soon as it exists. The wait is bounded so a hung first request cannot hold its duplicates forever.
- **Store kept answers in the ledger, so every worker and a restart see them.** The answers carry request text and the ledger keeps metadata only (INV-12); a retry that reaches another process runs again, which costs money but stays correct.
- **De-duplicate `seen` by time alone, for every caller.** The simulator and the mock warm-up repeat requests within seconds on purpose; counting those once would change every simulation number and the pinned reference runs. Only a gateway request has a sender.
- **Track the retry window in the router.** The router does not see whether an `add_example` inserted or bumped, and two concurrent retries could both pass a check made before the write; the ledger decides both under one lock.

## Consequences

- A client that sends an `Idempotency-Key` pays for one cascade however often it retries within ten minutes, and gets the same answer each time; a client that retries without one still pays for each attempt, but its retries no longer move golden examples into training.
- Responses gain `Idempotent-Replayed: true` on replays; the 400 and 409 codes above are new; `requests.retry_count` and the chat log line's `retry_count`, `idempotent_replay` and `replay_of` (the id of the request that ran) fields say which requests were retries. A replay's log line has `cost_usd` 0, so a sum over the log lines counts each cascade once. `ratchet_idempotent_requests_total{outcome}` and `ratchet_seen_skipped_total{reason}` count both mechanisms; replays are not in `ratchet_requests_total`, since no cascade ran.
- A genuine repeat of the same request from the same API key within five minutes now counts once in live mode, so a frequent request moves to training a little later. Repeats from other API keys, and repeats minutes apart, count as before.
- The idempotency cache and the seen window are per process: a gateway with several workers de-duplicates per worker.
- `ADR 0007` gains an amendment pointing here.
