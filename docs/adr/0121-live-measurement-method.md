# ADR 0121: Live measurement method: synthetic traffic through the public API in rounds, a measured all-Ultra control arm and one results file behind every live number

- Status: Accepted
- Date: 2026-10-21

## Context

PRD §8.2 asks for a live run on Token Factory and Nebius AI Cloud with real numbers in the README and the video, and for the real Nebius bill (failed jobs included) next to the cost report's break-even line. The ROADMAP's Oct 25 row asks for at least 3 versions trained on live traffic with real cost and precision numbers. NFR-1's p50 target is `untested (live)`. The submission text held 9 `[LIVE NUMBER]` values and the demo script 3 more, and nothing in the repository could produce them reproducibly: `sim.simulate` runs mock models in process, and `python -m ratchet.live` has `night`, `tick`, `reload` and `seal` only.

The "before" side of every saving was an estimate too. The router prices a student-served request's all-Ultra baseline as the student's own tokens plus `RATCHET_TEACHER_REASONING_TOKENS` (300) per choice; nobody had measured what Ultra would have spent on those requests.

Three facts shape the method:

- A live ledger's day is wall-clock time since its first request (`auto_day`), not a round, and `run_night` does not read the day. Rounds have to be keyed some other way.
- Live mode audits little by default (`RATCHET_AUDIT_RATE` 0.05, `min_audits` 20). With a 10% canary and a 0.7 student share, the first canary stage needs about 7,398 requests for a 90% chance of 20 audits (`stats.binom_sf`); with `RATCHET_CANARY_AUDIT_RATE=0.5` (audit focusing, ADR 0025) it needs about 737.
- The judges are Nebius and NVIDIA staff, and the past winners the submission cites were chosen for measured results, reproducibility among them.

## Decision

- **Traffic only through the public API, with a dedicated key.** `python -m ratchet.liverun` sends the workload's own seeded requests (`sim.world.make_stream`, imported lazily, or a JSONL file with its own labels) to `/v1/chat/completions` with the key named `--client` (default `liverun`), read from `RATCHET_LIVERUN_KEY` and never from a flag. It calls only `/healthz` and `/v1/chat/completions` on the gateway, never `/ratchet/*` (so never a demo route, INV-8), and reads the gateway's ledger file directly. A round is the id range `(after_id, upto_id]` of `requests` filtered by the key's name (`Ledger.client_window`); rows of other clients inside the range are counted as `other_clients` and left out. Items are drawn in index order before a batch is sent, so concurrency never changes which texts are sent, and every request carries `X-Client-Request-Id: liverun-<run_id>-r<round>-<index>`.
- **Preflight before any paid call.** The gateway's startup checks, `require_distillable` on the teacher, the gateway's task registry, the key, `/healthz` answering `mode: live` (a mock gateway is refused), a training command that runs on this host, an open `student_endpoint` interval, the planned gate profile, and a plan within `--max-usd`. Then one probe request proves the gateway writes the same ledger file under the key's name, with the audit rates this shell reads.
- **Nights in process through `live.main`'s seams.** Between rounds the harness calls `live.main(["night"])` and, after a round's traffic has stopped, `live.main(["tick"])`, with its own `provider_factory`, `run` and `http`. The outcome is read from the ledger's events (`Ledger.events_since`), never from the report text. `--until-settled` sends extra batches while a version is in shadow or canary; an unsettled release is recorded, and the next night then skips by itself (INV-5). A failed night records the exception's class, writes results and stops; a resumed run tries it again first.
- **The planned gate profile.** `run` refuses to start unless `RATCHET_SEQUENTIAL=1` (the anytime-valid canary rule) and `RATCHET_CANARY_AUDIT_RATE=0.5` are in force, so a canary's stages get their audits within a round and its decisions keep their error guarantee however often the gate runs. `--gate-profile as-set` measures other settings on purpose, and the results say which were in force.
- **A Bernoulli control sample, a ratio estimator on student-served rows only, randomised call order.** Request `(k, i)` is also sent straight to the teacher when `Random("seed:control:k:i") < --control-share`: independent of routing, cost and content, and reproducible on resume. The call is exactly `Ratchet._teacher_complete`'s for the serving role (the request validated and normalised as the gateway does, `GenPolicy.plan(...).serve`, one choice), priced as the router prices a call. It goes from the harness to Token Factory, never through the gateway or the ledger, so it can never become an example or a golden row (INV-2, INV-10). For student-served pairs (x the recorded `all_teacher_cost_usd`, y the control call's cost) `R_s = stats.ratio_estimate`; teacher-served rows keep their recorded baseline, which is a real Ultra call (`R_t` is reported as a check, about 1). The measured baseline is `B = Σx_teacher + R_s Σx_student`, with a normal-approximation 95% interval and no finite-population correction; fewer than 10 student-served pairs is `insufficient`. Which arm calls first is a second independent draw, because whether Token Factory caches prompts is unverified. The arms may use their own Token Factory key (`NEBIUS_API_KEY_LIVERUN`). The control arm has its own cap (20% of `--max-usd` by default), and each call reserves the most expensive call so far before it is sent, so concurrent workers cannot overshoot it together.
- **Template-label accuracy apart from agreement with the teacher, hard templates apart.** Each answer is scored with the task's own spec (`task.key`, each `FieldSpec.match`) against the item's labels, and an invalid answer counts as wrong. The labels are labelled as what they are: "synthetic tickets, template labels" (the template author's, independent of the teacher only in that the teacher never wrote them) or "the file's labels". Agreement with Ultra on paired student-served rows and the ledger's audited precision (Clopper-Pearson lower bound, Wilson interval) are reported beside them, never in their place.
- **The cap from the ledger, the compute intervals and the arms, with the server cap as backstop.** Before every batch: the key's teacher spend since the run started, the hosted student's tokens when there is no endpoint, else the endpoint's GPU-hours since the run started, training GPU-hours, and the arms' own spend. The run stops with `max_usd` when that plus the next batch's projection (the p95 cost per request so far, times the batch, times 1 + the control share) would pass the cap. A batch already sent can overshoot by its own cost. The gateway's own per-key cap, when one is configured, is the backstop; its 429 stops the run with `server_cap`.
- **One results file with claim ids.** `results.json` (generator `ratchet.liverun/1`) holds the identity (run id, git SHA or `RATCHET_GIT_SHA`, a SHA-256 over the `ratchet` and `sim` sources, the version), the models as Token Factory and vLLM list them, the non-secret settings, the plan, each round's ledger snapshot (taken when the round ends, so a later retention fold cannot move a published number) and client-side block, the arms, the cost, the KPIs by the PRD's formulas, and flat `values` with `live.*` ids and a one-line `sources[id]` each. A value that could not be measured is left out, never written as 0. `requests.ndjson.gz` holds per-request metadata only. No request or answer text, key or base URL is written anywhere. `verify` recomputes every client-side value from the records; ledger-side values are snapshots and say so.
- **One repeat run.** `--repeat-of RUN_DIR` runs the same plan, workload and seed again into a new run directory, and its results compare every value with the first run's (`repeat`); `report RUN_DIR --repeat REPEAT_DIR` attaches the comparison to the first run and `--publish` copies the repeat beside it. Two runs show how much a number moves between runs; they are not a confidence interval, and the caveats say so.
- **Numbers reach the docs only from a published, non-smoke run.** `report --publish` refuses a smoke run, and a stopped run without `--allow-partial`. PRD statuses that wait on live evidence (NFR-1, FR-8.1, FR-8.2, FR-8.4, SM-1 to SM-5) move only in the commit that adds a published `evidence/live/results.json`.

## Consequences

- A live number is one run (two with the repeat) on synthetic data, at list prices until the day-1 checks verify them, and at the stated concurrency from the harness host.
- The measured baseline corrects only what the formula estimates; it adds no estimator to the request path and does not change `router.py`'s baseline.
- The harness writes to the gateway's ledger only through existing writers: `live.main` and three event kinds (`liverun_start`, `liverun_round`, `liverun_stop`), which label synthetic traffic in the live release log. No schema change.
- Per-route server-side percentiles come from the window's rows by the nearest-rank rule (`liverun.window_stats`). Lane D's `Ledger.latency_percentiles` and `requests.wall_ms` are not in this tree; when they land, `wall_ms` is read from the same rows and reported beside `latency_ms`.
- The harness needs a host where nights can run (the training command and `deploy/`): the stock gateway image cannot run them (DEPLOYMENT.md step 7).

## Alternatives considered

- **An all-Ultra arm on every request.** Doubles teacher spend for a number a 5% sample estimates with a stated interval.
- **Audits as the only baseline.** Audits are temperature-0 check-role calls and are already what the savings receipts calibrate on; the control arm measures the serving role the client would have paid for.
- **A generic load tool (k6, locust).** No ledger windows, no labels, no nights, no control arm.
- **Nights as subprocesses.** A second process layer that `live.main`'s seams already make unnecessary, and one more place for the environment to differ.
- **Keying rounds by ledger day.** A live day is wall-clock time since the first request, so a round can span two days or share one.
