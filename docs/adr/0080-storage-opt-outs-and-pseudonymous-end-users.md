# ADR 0080: Storage opt-outs at every level, and end users kept only as scoped keyed hashes

- Status: Accepted
- Date: 2026-10-20

## Context

Until now every escalated, audited or arbitrated teacher answer became a training example, kept for good. The only way to keep a request out of the training set was to pin its whole task, which also takes the student away from it. That blocks regulated customers: a bank cannot send a request that must not be retained, a client cannot promise its own users an opt-out, and an operator cannot run Ratchet as a pure router while legal reviews its data terms. `RequestMeta.storable` existed in the router since ADR 0017, but nothing set it.

OpenAI's `store` field already means "keep this completion" (for distillation and evals), and its `user` and `safety_identifier` fields name the end user. Clients send them today; Ratchet validated and dropped them. Recording who sent a stored example matters too: a client leaving, or one of its users asking to be forgotten, needs the examples traced back, and nothing recorded that.

## Decision

- **Five opt-outs, broadest first** (`privacy.OPT_OUTS`): `global` (`RATCHET_STORE_EXAMPLES=0`, zero retention), `task` (a spec's `store: false`, or `RATCHET_NO_STORE_TASKS`), `key` (`store=0` for the API key's name in `RATCHET_KEY_LIMITS`), `request` (`store: false`, `X-Ratchet-Store: none|0|false`, `metadata.ratchet_store` `"false"|"0"`) and `end_user` (a no-train registration). The first that applies is recorded in `requests.store_opt_out` and returned in `ratchet.store_opt_out`.
- **Opt-outs only remove storage.** `Ratchet.store_opt_out` is checked once at the start of `handle` (`_opted_out`, so the row records the reason) and again in `_store_example`, the only writer of examples. Nothing in a request can undo one: `store: true` and `X-Ratchet-Store: 1` are the default spelled out. An unknown header or metadata value is a 400, so a typo cannot store by accident, and `RATCHET_STORE_EXAMPLES` refuses anything but a clear switch at startup. The proposed invariant is in `docs/lanes/e-invariants.md`.
- **The cascade does not change.** An opted-out request is sampled, served, audited and arbitrated as any other, so release statistics never depend on what was stored. Only `add_example` is skipped, and an opted-out duplicate neither bumps `seen` nor records its client. An absent `store` means store: Ratchet's default is the opposite of OpenAI's, because distilling is its purpose; the API docs say so.
- **Zero retention stops training.** `run_night(store_examples=False)` skips before anything else (`storage disabled`): nothing new can arrive, and training on examples kept from before is not what an operator who switched storage off expects. One step still runs when no release is in flight: a task whose spec changed is re-scored on the stored golden rows (it writes only the version's eval, no example), because the router keeps such a task on the teacher until a re-score, which would otherwise never come.
- **End users are a keyed hash, scoped to the API key.** `safety_identifier` (else `user`, any length, hashed whole) becomes `HMAC-SHA256(key, client_name + NUL + value)[:16 hex]` (`privacy.EndUsers.hash`). The key is `RATCHET_END_USER_KEY`, or 32 random bytes generated once into the ledger's `meta` table, so hashes survive restarts and differ between deployments. Only the hash reaches the router and the ledger (`requests.end_user`, indexed with `ts`; `examples.end_user`); the raw value never leaves `gateway._request_meta`, never appears in an error, and was never forwarded upstream.
- **Why scope by key.** The spec this item came from hashed the value alone. Keys are tenants (ADR 0022's `clients`, per-client receipts), and an unscoped hash would let the operator link one person across two customers' apps, and let one client opt out another client's users by guessing identifiers. With the key name in the message, the same identifier from two clients is two people as far as the ledger can tell. The cost is that an opt-out does not follow a person across a company's several keys; an admin registers across every key (below), and a single key per user base avoids it. The scope is the key's name, not its secret, so rotating a key keeps every hash; renaming one unlinks its client's registrations, which then match nothing. Startup counts those (and keyless registrations while keys are on) and writes a `no_train_unmatched` event once per change; `/ratchet/stats` keeps the count (`privacy.no_train_unmatched`).
- **No-train registrations.** `POST /v1/ratchet/no-train {"end_user": ...}` stores the hash in `no_train(end_user_hash, ts, client, admin)`. It is open wherever chat completions are (an opt-out only removes storage): an API key registers its own end users; an admin key names a `client` or, by default, registers one hash in the every-client scope (`privacy.EVERY_CLIENT`, `*`, never a key name), which every request also looks up, so keys added later are covered. `DELETE` (same body, never a query string, which access logs keep) removes a registration: an API key its own but not an admin's; an admin any; and without API keys a live gateway refuses it unless an admin key is sent, so nobody can switch storage back on for someone else. Events say how many and who, never the end user or its hash, because `/ratchet/stats` is public; the responses do not return the hash either, so the endpoint cannot be used to compute hashes for guessed identifiers.
- **Every identifier a request carries is matched.** The request is attributed to `safety_identifier` (else `user`), but a no-train registration made with either value applies (`privacy.end_user_ids`, `EndUsers.aliases`, `RequestMeta.end_user_aliases`): a client that registered `user` values and then follows OpenAI's advice to send `safety_identifier` keeps its opt-outs. The other hashes are looked up in one query and never stored.
- **Any length.** `user` and `safety_identifier` were accepted at any length before Ratchet read them, so a cap (the spec's 128 characters) would have broken clients that send long identifiers. The value is hashed whole, never cut, so two long values sharing a prefix stay two end users; the body limit bounds it.
- **Who is told what.** `created` (POST) and `status` (DELETE) say whether a registration existed. They go to API keys and admin keys only: without API keys anyone may call the endpoint, so a keyless caller gets `null` and cannot use it to learn whether someone opted out.
- **Examples record their sender.** `examples.client` and `examples.end_user` hold the first request's; a duplicate from another client adds `(hash, client)` to `example_clients`. This is what erasure and export by client need.
- **Per-key settings.** `RATCHET_KEY_LIMITS` uses the syntax planned for spend and rate limits (`name:field=value,...;name:...`) with one field, `store`. Every other field is refused until it is built, and an unknown name is reported without quoting it, in case a key was pasted where its name belongs (invariant 13).

## Consequences

- Regulated clients can use the cascade without contributing data, at the price of their traffic never improving the student. A deployment with zero retention is a router with audits and a release gate that never releases anything new.
- `/ratchet/stats` grows (only adds keys): `privacy.not_stored_requests`, `not_stored_by_reason`, `no_train_end_users`, `store_examples`, `no_store_tasks`, `no_store_clients`, `end_user_key`, and per client `end_users` and `stored_share`. The response's `ratchet` block adds `stored` and `store_opt_out`, and `metadata` is echoed.
- The generated key lives in the database file and its backups. Anyone with the file can test guessed identifiers against the hashes; setting `RATCHET_END_USER_KEY` from a secrets manager keeps the key out of the file. Changing the key unlinks every earlier hash and every no-train registration; startup writes an `end_user_key` event with the count.
- Opt-outs are not erasure: examples stored before an opt-out took effect stay until an erasure item removes them. A duplicate's later end users are not recorded (only its clients).
- One primary-key lookup per request that names an end user (up to four hashes in one query), and one more just before a store, so a registration made while a request waits for the teacher still holds; that late opt-out is reported in the row and the response like one found at the start.
- Every writer of examples must honour these opt-outs. `_store_example` is the only one in this tree; a test asserts that every entry of INV-2's `add_example` allowlist asks `store_opt_out` first, so a later writer (a backfill) cannot skip them.
- `RATCHET_KEY_LIMITS` is shared with the planned spend and rate limits; whoever builds them extends `auth.KeyLimits` and `KEY_LIMIT_FIELDS` instead of adding a second variable.
