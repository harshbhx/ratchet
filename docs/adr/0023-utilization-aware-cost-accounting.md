# ADR 0023: Utilization-aware cost accounting

- Status: Accepted
- Date: 2026-10-20

## Context

Until v0.5 every savings figure priced a student answer per token, at the hosted Nano price (`DEFAULT_PRICES["student"]`). The self-hosted student does not bill that way. A Nebius Serverless Endpoint bills GPU-hours while it runs, whether requests arrive or not, and each night's training job bills GPU-hours too. At low utilization a student answer costs far more than the per-token proxy, so the savings Ratchet reported were overstated, and nothing in the product said so.

Nebius's own Serverless AI Builders Challenge found the same thing: its second-place project measured that self-hosting beats Token Factory on cost only at high utilization ([winners post](https://nebius.com/blog/posts/serverless-ai-builders-challenge-winners)). With unverified list prices (an L40S at about $1.55 per GPU-hour, about $0.001 of Ultra spend avoided per ticket-triage answer in the simulation) self-hosting breaks even near 1,500 student-served requests per endpoint hour, about 36,000 a day. The demo's 1,500 requests a day do not pay for a 24/7 endpoint. Ratchet has to say that itself, with the numbers.

## Decision

- **Split each request's cost, change nothing else.** `requests` gains `student_cost_usd` (the student's samples, live and shadow), `teacher_cost_usd` (escalation, audit, arbitration, pinned) and the student calls' tokens (`student_in_tokens`, `student_out_tokens`). `Ratchet.handle` adds each call's price to its part next to `cost_usd`, which is still summed call by call exactly as before, so `cost_usd` equals the parts up to float rounding and every stored number, the `/ratchet/stats` figures and the pinned reference simulation stay as they were. Rows from before v0.5 have no split: the report counts their whole `cost_usd` as teacher spend (which can only lower the GPU-hour view's savings) and says how many there are.
- **Record when GPUs ran.** A new `compute_intervals` table holds `student_endpoint`, `training_job` and `eval_job` intervals: start, end (NULL while running), USD per GPU-hour and GPUs as recorded, the version a training job produced, the source and a note. Writers: `python -m ratchet.cost endpoint up|down` (and `close KIND` for a job whose end was lost), `POST /ratchet/cost/endpoint` (admin key; open in mock mode like the other management calls), `deploy/student_endpoint.sh` start and stop (best effort, through the CLI), `run_night` around `trainer.train()` in live mode (wall-clock time, closed also when training raises, then re-raised; it includes the upload and adapter load, so it is an upper bound), and the simulator (closed records of their own, `Ledger.compute_record`, so a simulated day never closes or reuses an interval someone opened). Rates are bounded wherever they are set or recorded (0 to $1,000 per GPU-hour, 0 to 1,024 GPUs), so every total stays finite. Starting a student endpoint that is up returns the open interval (one transaction, so a second process cannot open another); stopping it closes every open one. Each interval keeps the rate it was recorded at, so changing a setting never reprices history.
- **One clock per ledger.** A live ledger records on the wall clock and counts days from its first request, as `auto_day` always has. A simulated day takes about a second, so its 24 hours cannot be on the wall clock: simulations and tests use a synthetic clock where day N starts at N x 86400 s (`Ledger.now`, `day_start`, `day_of`). The simulator records one endpoint interval per day of `RATCHET_MOCK_ENDPOINT_HOURS` (24) and one training job per trained version, 600 s plus 0.05 s per training example from 22:00: simulation assumptions, which write intervals only, so no request, event or random draw moves.
- **Merge, never double-count.** Intervals of one kind are merged into disjoint segments; where records overlap, the segment is billed at the highest rate among them (a sweep with a heap, O(k log k)). Two records of one endpoint count once and never at less than either says. An open interval runs to now.
- **Report both views.** `ratchet/cost.py` `cost_report(ledger, settings, since, until, now, days)` reads one aggregate query over the requests (by ledger day) and the intervals clipped to the window, and returns:
  - `per_token`: total = Σ `cost_usd`, as every figure until now.
  - `gpu_hours`: total = teacher spend + endpoint GPU-hours + training GPU-hours + the student's per-token spend in hours (a live ledger; days on the synthetic clock) with no recorded endpoint uptime (the hosted fallback served then, or nobody recorded the endpoint; a warning counts those answers). Savings = all-teacher baseline − total, negative when self-hosting does not pay, never clamped.
  - s̄ (`avoided_teacher_usd_per_student_request`) = Σ over student-served requests of (baseline − teacher spend) / student-served requests.
  - R (`endpoint_usd_per_hour`) = the endpoint's GPU cost in the window / its hours: the rate the intervals recorded (per-GPU price x GPUs), the same the GPU-hour view bills; the configured rate only while no uptime is recorded.
  - break-even (`break_even_student_requests_per_gpu_hour`) = R / s̄; null when s̄ ≤ 0. It prices the endpoint's hours alone, not training.
  - h̄ (`hosted_fallback_usd_per_request`) = the fallback student's per-token price of every student call's tokens in the window / the student-served requests among them: what the hosted fallback would bill per answer it serves. The crossover (`self_host_beats_hosted_above_requests_per_hour`) = R / h̄. It compares price per answer only, so it assumes the hosted fallback serves as many requests as the tuned student.
  - observed (`observed_student_requests_per_endpoint_hour`) = student answers in buckets with endpoint uptime / endpoint hours; `utilization_vs_break_even` = observed / break-even.
  - idle hours = endpoint hours in buckets when no request reached the student. A bucket (`idle_granularity`) is an hour on a live ledger, where requests and intervals share the wall clock, and a whole ledger day on the synthetic clock.
  - a `daily` breakdown (the latest 731 days at most), open intervals and warnings (a job open for more than 12 hours, rows without a split).
  `RATCHET_STUDENT_COST_MODEL` (`per_token`, the default, or `gpu_hours`) picks the `headline` view and nothing else.
- **Recommend one thing.** `self_host` when observed ≥ break-even and ≥ the hosted crossover; otherwise `scale_to_zero` when more than half the endpoint's hours were idle; `insufficient_data` when no uptime is recorded or the student served nothing yet; `hosted_fallback` when observed is below the crossover; and `scale_to_zero` again in the rare remaining case (below break-even, and a hosted fallback that costs more per answer than the teacher spend it avoids), with the explanation saying the endpoint has to run fewer hours. An `explanation` gives the numbers and the price label, and says two things separately so the words never contradict the figures: whether the observed volume covers the endpoint's hours (at or above break-even, or below it), and whether the window still lost money by GPU-hours (training is not in the break-even). Between break-even and the crossover it says that self-hosting beats the teacher and that the hosted fallback would cost less per answer, with the caveat that the crossover assumes equal coverage; it never says "pays" when the GPU-hour savings are negative.
- **Say how sure the prices are.** GPU rates come from `RATCHET_STUDENT_GPU_USD_PER_HOUR`, `RATCHET_STUDENT_GPUS`, `RATCHET_TRAIN_GPU_USD_PER_HOUR` and `RATCHET_TRAIN_GPUS` (L40S list price, 1 GPU), checked at startup (a bad value names its variable). Every report says "unverified list prices" until an operator sets `RATCHET_PRICES_VERIFIED=1` after the day-1 checks pass and the rates match the Nebius bill (INV-9).
- **Serve it.** `GET /ratchet/cost?days=N` (public, like `/ratchet/stats`), a compact `cost` block in `/ratchet/stats` (`model`, `endpoint_hours`, `gpu_hours_savings_pct`, `break_even_student_requests_per_gpu_hour`, `recommendation`; added keys only) with `totals.cost_model` naming the per-token view the other figures use, and `python -m ratchet.cost report [--days N] [--json]`. The CLI opens an existing ledger file only, so it never creates an empty one where it was not asked to.

## Consequences

- Demo volumes do not pay for a 24/7 endpoint, and Ratchet now says so: the mock demo and the simulator show positive per-token savings and negative GPU-hour savings, with the recommendation `hosted_fallback` (simulation). At customer volumes (10M requests a month, about 14,000 an hour) the endpoint's GPU-hours cost far less than the teacher spend they avoid, so the GPU-hour savings are positive, and the report still says `hosted_fallback`: per answer the untuned hosted Nano (about $0.00003 at list prices and the simulation's token counts) beats a $1.55-an-hour endpoint below roughly 52,000 student answers an hour. That comparison assumes the hosted model serves as many requests as the tuned student, which the fine-tuning exists to beat; the explanation says so, and an operator compares the student's share over a day on each before switching.
- The levers are visible in the numbers: serve many LoRA adapters (tasks or customers) from one GPU with vLLM multi-LoRA, scale the endpoint to zero between bursts, and use the hosted fallback below break-even.
- Uptime is only as good as its records. An endpoint nobody recorded costs nothing in the report; its student answers are priced per token and counted in a warning. A job whose process died stays open and counts up to now until someone closes it, which overstates rather than hides the cost.
- Idle time and the observed volume are counted by hour on a live ledger, so a 24/7 endpoint that sees one request a day is idle 23 hours in 24, and answers in hours with no recorded uptime go to the hosted fallback rather than to the endpoint. The simulator's requests carry wall-clock times that its synthetic intervals cannot be compared with, so there they are counted in whole ledger days, and hours idle inside a busy simulated day are not counted. An hour with any uptime is credited with all its answers. The savings figures are exact either way.
- The training interval in live mode is the wall-clock time of `trainer.train()`, an upper bound on the Serverless Job's billed time.
- A per-request `cost_usd` is still the per-token proxy; the GPU-hour view exists only in the report, so receipts (FR-15.5) and later items build on the split columns and the report rather than on a rewritten history.
- Two more columns of tokens per request (the hosted-fallback price needs tokens, not dollars, because input and output prices differ) and one more table; old files gain them on open.

## Alternatives considered

- **Price student calls in GPU-hours per request** (amortize the endpoint's hourly price over the requests of each hour). Rejected: it rewrites `cost_usd`, moves every historical number and the reference simulation, and an idle hour has no request to carry its cost.
- **Read uptime from the Nebius billing API.** Better data, but no such API is verified for Serverless Endpoints yet, and the gateway would need cloud credentials. Recorded intervals work offline and in tests; reconciling with the bill stays a manual check (`RATCHET_PRICES_VERIFIED`).
- **Day granularity everywhere.** One rule for both clocks, but on a live ledger it reported a 24/7 endpoint with one request a day as never idle and credited a whole day's answers to an endpoint that ran for one hour of it. Live ledgers use hours (one more aggregate query); the synthetic clock keeps days, because synthetic request times would move the reference simulation.
- **Compare totals with the hosted fallback, extra escalations included.** It needs the hosted model's coverage, which Ratchet does not measure (the hosted fallback is not served beside the tuned student), and a configured guess would read like a measurement. The explanation states the assumption instead.
- **A `teacher_only` recommendation** for the case where neither the endpoint nor the hosted fallback pays. Left out to keep the four outcomes the PRD names; the explanation says it plainly instead.
