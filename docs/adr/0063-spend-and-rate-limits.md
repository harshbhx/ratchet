# ADR 0063: Spend and rate limits: per-key budgets, a gateway budget with a student-only mode, and limits that refuse instead of queueing

- Status: Accepted
- Date: 2026-10-21

## Context

The only limit on `/v1/chat/completions` was one daily request count per key (`RATCHET_API_KEY_DAILY_REQUESTS`), and it ran `SELECT COUNT(*) ... WHERE client=? AND ts>=?` on every request, under the ledger's one lock. There was no way to cap what a key, or the gateway, spends in US dollars, so a client in a loop, a leaked key or an open live gateway (threat model T11, T19) could spend the operator's Token Factory credit until someone noticed the bill. Nothing limited how fast a key may send or how many requests it may hold at once, and a burst past the 40 worker threads queued inside the server, where it also blocked the dashboard and the health check. Every key could send every task, and every key's traffic became training data.

The limits had to stay off the hot path's cost (one query per request was already too many), survive a restart, apply to `/v1` only (Scout has its own budget guard, invariant 11), and be keyed by key name only (invariant 13).

## Decision

- **One syntax for a key's limits.** `RATCHET_KEY_LIMITS='acme:daily_requests=10000,daily_usd=5,monthly_usd=100,rpm=60,concurrency=4,tasks=ticket-triage|invoice-extract,store=1;globex:daily_usd=1'`, parsed at startup into one `auth.KeyLimits` per key name over the defaults (`RATCHET_API_KEY_DAILY_REQUESTS`, `_DAILY_USD`, `_MONTHLY_USD`, `_RPM`, `_CONCURRENCY`; 0 = off). A name that is not in `RATCHET_API_KEYS`, an unknown field, a field or a key given twice, or a bad value raises `ValueError`, as `KeyRing` does; the message lists the key names and never echoes an unknown entry, which may be a key pasted in the wrong place. `RATCHET_API_KEYS` keeps its syntax.
- **An in-memory spend meter (`ratchet/spend.py`).** `SpendMeter` keeps answered requests and dollars per (key, UTC day), dollars per (key, UTC month) and the gateway's dollars per UTC day, behind one lock. It reads the ledger once, at startup: today's requests and the spend of failed requests (`failures.cost_usd`), and this month's when a monthly cap is set, counting only rows with a gateway request id, so Scout's agents and the simulator (which call `handle` without one) are never counted. Then the gateway adds each request's `cost_usd`, or what a failed request spent before failing (`RequestContext.spent_usd`, filled by the router); a job whose cost for a request lands later adds it with `requests=0`. The quota and budget checks read memory: the request path runs no query for them.
- **Rollover.** A new UTC day (or month) starts from zero instead of reading the ledger again: a request logged before such a read and added after it would count twice. A clock that moves back to an earlier day reads the ledger, since memory holds nothing for it. A request is counted on the day its add runs, so one that ends just after midnight counts toward the new day until a restart.
- **Checks and answers.** After the task is resolved and before the cascade: the key's task scope (403 `task_not_allowed`, before any quota, so it costs nothing; an unknown-task 400 lists only the scope's tasks), the daily request quota (429 `insufficient_quota` / `daily_quota_exceeded`, as before), the key's dollar budgets (429 `insufficient_quota` / `budget_exceeded`, with `X-Ratchet-Budget-Remaining-USD: 0`, `Retry-After` and `X-Ratchet-Budget-Reset` for the cap that resets last, and `X-Should-Retry: false`), then the gateway's budget. A key with a dollar cap gets `X-Ratchet-Spend-Today-USD` and `X-Ratchet-Budget-Remaining-USD` on every answer. A check reads what was spent before the request, so a request in flight can overshoot a cap by its own cost.
- **The gateway's budget and its two modes.** `RATCHET_DAILY_BUDGET_USD` (0 = off) counts every `/v1` chat request's spend. `RATCHET_BUDGET_MODE=block` answers every chat request 429 `gateway_budget_exceeded` until 00:00 UTC (`/v1/models` and lookups cost nothing and still answer). `student_only` sets a per-request flag, `RequestMeta.student_only`: `handle` serves a confident student answer with an effective audit rate of 0 (the random draw is still made, so the stream of draws is unchanged) and no shadow, and raises `spend.BudgetExceeded` before any teacher call for a request that needs the teacher: an escalation, a cold start, a pinned or unregistered task, or `tools`, which the student does not see. The gateway answers it with the same 429. What the escalation's student samples cost is a failed request's spend: a `budget` failures row (never throttled), the metrics, and the key's budget. Without audits, canary promotion pauses; rollback still acts on the audits recorded. The gateway's budget amount is never named in a client's message.
- **Budget alerts.** The first time a key or the gateway reaches each `RATCHET_BUDGET_ALERT_PCT` share (`50,80,100`) of a dollar cap in its UTC day or month, the meter writes a `budget` event (`acme reached 80% of $5.00 daily budget`, `the gateway reached ...`; a key name has no space, so it can never read as the gateway). It parses the period's `budget` events at startup (index `events_kind_ts`), so a restart writes none twice, and writes at once the shares a lower cap has already passed. An event that cannot be written is tried again on the next add; it never fails the request that crossed the line.
- **Rate limits that refuse (`ratchet/ratelimit.py`).** On the event loop, in two steps. After the API key and before the body is read (`_rate`, `Limiter.rate`): the key's requests a minute (`rpm`: a token bucket with a burst of `max(1, rpm // 6)` refilled continuously; 429 `rate_limit_exceeded` with `Retry-After` and OpenAI's `X-RateLimit-*-Requests` headers), or on a gateway without keys the client address's (`RATCHET_IP_RPM`, 120 a minute in live mode, off in mock mode; `_client_ip`, which honours `RATCHET_TRUST_PROXY`; at most 10,000 addresses, least recently seen dropped). A refused request takes no token. Once the body is in, just around the worker thread (`_hold`, `Limiter.hold`): the gateway's chat requests in flight (`RATCHET_MAX_INFLIGHT`, 32, below the 40 worker threads; 503 `overloaded`, `Retry-After: 1`), then the key's (`concurrency`; 429 `rate_limit_exceeded`, `Retry-After: 1`), given back when the response is built. The caps protect the thread pool, so they count only requests that are about to use it: a client that trickles its body (nothing in front of uvicorn times a body out) holds no slot, and cannot refuse everyone else's requests by opening slow uploads. A request refused there has used its rate token. On a 200, the daily quota's `X-RateLimit-*-Requests` headers win over the bucket's, as since v0.4.
- **Per-key storage.** `store=0` makes every request of the key `RequestMeta.storable=False`: served, audited and logged, never stored as training data (a tenant that opted out of training).
- **Scrubbed reads.** An anonymous read of a public live dashboard (ADR 0061) names no key and no dollar cap: a `budget` event reads `client-1 reached 80% of its daily budget` (`spend.public_alert`, through `access.scrub_event`), and `clients[].daily_cap_usd`, `budget.daily_usd` and `budget.remaining_usd` are null, as the gateway's 429s never name its budget. Startup errors for `RATCHET_KEY_LIMITS` quote an item, field or value only when it is shorter than any key (16 characters), so `acme:<key>` pasted in `RATCHET_API_KEYS`' syntax is never printed.
- **Observability.** Refusals get `quota`, `budget` or `rate` failures rows (the gateway's throttled ones; the router's for a refusal that spent money) and `ratchet_rejections_total` reasons `budget`, `rate` and `overloaded`; `/metrics` gains `ratchet_inflight_requests`; `/ratchet/stats` gains `clients[].spent_today_usd`, `clients[].daily_cap_usd`, a `budget` block and three `security` keys.

## Alternatives considered

- **Count in the ledger on every request** (the old quota, extended to dollars). One aggregate per request per limit, under the ledger's lock, on a table that only grows. The meter reads memory and the ledger once.
- **Read the ledger again at every rollover**, as first proposed. It can count twice a request logged before the read and added after it. A single process sees every gateway request it serves, so starting the new period from zero is exact; the ledger is read only when memory cannot be right (startup, a clock moved back).
- **A global `Ratchet.flags.student_only`**, as first proposed. Scout's agents call the same `Ratchet`, and its pinned planner and writer would have failed whenever `/v1` spent its budget, against invariant 11; a flag on each request also needs no lock.
- **Run the shadow in `student_only` mode without arbitration.** An unarbitrated disagreement counts against the candidate (ADR 0013), so a spent budget would bias the release gate against it. No shadow at all is neutral.
- **Queue requests past a limit.** A queued request holds a connection and, past the thread pool, blocks routes that cost nothing (the dashboard, `/healthz`). A 429 or 503 with `Retry-After` lets the client wait instead; OpenAI SDKs honour it.
- **Rate-limit after validation.** Validation needs the body, which needs a thread; limiting first refuses a flood without reading anything. The cost is that a request refused later has used its token, which is how OpenAI counts requests too.
- **Take the in-flight slots before the body is read**, as first built. A refusal then read nothing, but a slot was held while the client sent its body, and nothing times a slow body out: 32 stalled uploads from one client (or from anyone on the keyless mock demo) made every other chat request a 503, though none of them used a worker thread. Reading the body first costs a connection's buffer, which the body limit (413) bounds.
- **Limits shared across processes** (Redis, the ledger). The gateway runs one worker (ADR 0006); a shared store is a new dependency for a deployment that does not exist yet.

## Consequences

- A leaked or looping key spends at most its budget; the gateway at most its own, and in `student_only` mode it keeps serving what the student can answer alone. Operators see 50, 80 and 100% before the refusals start.
- The quota check no longer touches SQLite; startup reads today's (and with a monthly cap this month's) rows once, a pass over an index.
- The meter and the limiter are per process: with several workers each would enforce its own share. A request in flight can overshoot a cap by its own cost, and concurrent requests by theirs.
- Limits apply to `/v1/chat/completions`. A later OpenAI-compatible endpoint that calls the cascade should go through `_rate` before its body, `_hold` around its worker thread, the same checks in `_complete` and `SpendMeter.add`.
- Dollars are per-token list prices, unverified until the day-1 checks pass (invariant 9); endpoint GPU-hours are not part of them.
- No decision or simulation number moved: the reference simulation and the three pinned workloads never set a limit.
