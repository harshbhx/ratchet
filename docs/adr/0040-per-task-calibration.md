# ADR 0040: Per-task calibration when several tasks share one adapter: thresholds, a per-task golden gate, and per-task alerts

- Status: Accepted
- Date: 2026-10-20

## Context

One adapter often serves several tasks: Scout's triage and reader calls next to support tickets (the `mixed` workload), or a company's own tasks registered through the task registry (UC-06). Until now everything after the student's samples treated them as one:

- `cascade_eval` calibrated one threshold over the pooled golden rows. The student is rarely equally good at every task. The easy tasks' right answers dilute a hard task's wrong ones, so the pooled threshold serves the hard task below the target precision (97%). When the hard task pushes the threshold up instead, the easy tasks are held back.
- `ReleaseGate.admit` read the pooled precision and coverage only. A candidate that got one task badly wrong shipped if the others hid it.
- `Ratchet.threshold` ignored the task, apart from the spec-change check of [ADR 0022](0022-task-registry.md).
- The live alert looked at a version's audits as a whole, so a task the student does badly never raised it when the other tasks were fine.

## Decision

- **One record per task in every eval.** `cascade_eval` scores each golden row once and splits the rows into calibration and held-out halves by their global position, exactly as before, so the global numbers do not move. Each point also goes into its task's lists, and `eval['tasks'][name]` holds `golden_n`, `test_n`, `agreement`, `threshold`, `precision`, `coverage`, `spec_hash`, `target_precision` and `calibrated`. With one task the record is the global numbers again: the tickets reference simulation is byte-identical.
  - A task's threshold is calibrated on its own calibration rows to its spec's `policy.target_precision` (default 97%), by the same rule as the global one.
  - With fewer than `RATCHET_MIN_TASK_GOLDEN` (20) calibration rows a task gets the higher of its own threshold and the global one (`calibrated: false`), so a few lucky rows cannot lower it.
  - A task with no held-out row gets 1.01: the student never answers a task that has a record without evidence measured on rows the threshold was not tuned on (INV-6). A task whose golden references are all invalid under its spec has a record with no rows, so it gets 1.01 too. A task with no golden row at all has no record and uses the version's global threshold, as every task did before.
  - `spec_hash` replaces `eval['spec_hashes']` as the record of the spec a task was scored under. `run_night` still writes `spec_hashes`, because it does not depend on the evaluator (a custom `Evaluator` may return no records), and readers check the record first (`calibration.recorded_hash`).
- **The router holds each task to its own threshold** (`calibration.threshold`, called by `Ratchet.threshold`): the task's record when its `spec_hash` is current, 1.01 when it is not (or when the older `spec_hashes` names another spec), else the version's global threshold. A version scored before this change has no records and keeps its one threshold. It is a dict lookup on a JSON object the request path already reads. `system_fingerprint` hashes the threshold the answer was held to, so each task of one version now has its own.
  - When the task's current record serves nothing (the gate disabled it, or it had no held-out row), the student is not called at all (`calibration.held_back`, route `task_disabled`): its samples could never be served, so they would only add a student call and its latency to every request of the task. With no student answer, `RATCHET_ON_TEACHER_FAILURE=serve_student` has nothing below the task's floor to stand in for the teacher. The shadow still runs. A task whose spec changed keeps the registry's path (the student is sampled and escalates, route `confidence`), and the hosted untuned fallback model ignores the records, as it ignores the version's threshold.
- **A per-task golden gate, the global gate's rule on each task's own rows.** After the global checks, which are unchanged, `ReleaseGate.task_failures` checks each task with at least `RATCHET_MIN_TASK_TEST_N` (10) held-out rows that the candidate would answer. A task fails when its held-out precision (over the answers it would serve) is below its floor (`policy.min_precision`, else `min_precision`), or below the live version's precision on that task less `tolerance`: point estimates, as for the global numbers, so a task that shares an adapter is held to what an adapter of its own would be. A task that answers none of its held-out rows has no precision to show and fails too, since the student would serve it without evidence. Live is compared only where it answers the task under the same spec with as many rows.
  - `RATCHET_TASK_MODE=disable` (the default) disables the task on the candidate (`Ledger.merge_task_eval` sets its threshold to 1.01 and `disabled` to the reason, in one transaction) and writes `task_disabled`; the version ships for its other tasks. `reject` rejects the candidate.
  - Either way, a candidate with records is rejected when the share of its held-out rows it would still answer, each task at its own threshold and the failing ones off, is below `min_coverage`. A version that serves (almost) nothing would wait in shadow or canary forever (no audits, no would-serve shadow answers), and no night trains while it does (INV-5).
- **A disabled task stays disabled for the version's life.** The champion re-check and a skip night's re-score overwrite a version's eval but run no gate, so `run_night` carries the disabled records over (`calibration.keep_disabled`), also for a task the re-score has no record for.
- **One alert per (version, task).** A new tick step, `_tick_tasks`, applies the live alert's rule (Wilson upper bound of audited precision below `live_floor`, at least `min_audits` audits in the current stage) per task, for the live version and the canary. A version whose audits in the stage are all one task's is left to its own alert and rollback, which say the same thing, so a single-task run writes nothing new. Once-only is read from the ledger's events in the transaction that writes the alert (`Ledger.event_once`: a `BEGIN IMMEDIATE` check and insert, a prefix comparison rather than LIKE because task names may hold `_`), so a new gate does not repeat it (each `python -m ratchet.live tick` builds one), nor does the gateway's tick racing a cron tick on the same file. Rollback stays per version, and nothing is disabled automatically on a live version: pinning a task is an operator's decision.
- **Stats and BOM.** `stats_by_task` adds the teacher's audits of each task (`audits`, `audit_agreement`) and, from the live version's eval, `threshold` (as the router applies it), `precision`, `coverage`, `calibrated` and `disabled`. The BOM's `eval` block carries the records written at training time; a later disable is a release decision, recorded in events and in the version's eval, never in the signed BOM (INV-14).
- `ratchet/calibration.py` holds the readers, pure functions over plain dicts, so the router, the gate, Night School and the stats read an older or hand-edited eval the same way. A record whose threshold is not a number sends its task to the teacher rather than guess.
- **An opt-out.** `RATCHET_PER_TASK_CALIBRATION=0` makes Night School write no records (`cascade_eval(per_task=False)`), so each new version keeps one pooled threshold and the gate checks only the pooled numbers, as in v0.4. Versions already scored with records keep them until a night re-scores them; the per-task alert and the stats read audits, not records, and stay on. The three reference workloads (`make reference`) run with it off, so they still reproduce v0.4.0 exactly.

## Consequences

- The noisy task of a shared adapter is served at the precision it was calibrated to, and the easy ones are no longer held back by it. With small golden sets the per-task thresholds are conservative, because a task's own threshold on a few dozen rows moves with every error near the top. In the mixed and research simulations (mock models, seeds 1, 2, 3, 7 and 11) the student serves less traffic than with one pooled threshold (final-day share 90–96% against 92–98% on mixed, 65–97% against 96–98% on research), and the lowest daily audit agreement is higher (96–98% against 93–96% on mixed); docs/TESTING.md has the table.
- The reference workloads (`tests/fixtures/reference.json`) stay v0.4.0's capture: `scripts/reference_check.py` runs them with `RATCHET_PER_TASK_CALIBRATION=0`. With the default on, the tickets workload has one task and is unchanged (the pinned reference simulation checks it), and the mixed and research runs move by design; their trend is checked in `tests/test_calibration.py` and their headline numbers are in the README.
- The global numbers are still measured at the global threshold, because the gate's global checks and every earlier version read them; the records describe what the version serves. Folding the records into the global checks, and certified per-task bounds, are left to certified precision (FR-16.3), for which the records are the interface.
- Changing a task's `target_precision` or `min_precision` changes its `spec_hash`, so the task goes to the teacher until the next night calibrates it under the new target.
- On the few dozen held-out rows a task has, a point estimate is noisy: a task at 97% shows under 95% on 30 rows now and then, and a candidate as good as live can show more than 2 points behind it. In `disable` mode a false alarm costs coverage on one task for one version, never precision; a candidate left answering under `min_coverage` is rejected, and the next night tries again. Two effects make that cost larger than one task's share. A version with a task disabled that live still answers usually loses the shadow's coverage comparison, so it is rejected after a day of shadow, a day no night trains (INV-5; research, seed 1). And a first version with a task disabled goes to its canary serving fewer requests, so it takes longer to collect the audits it needs (research, seed 11: until day 6). `RATCHET_MIN_TASK_TEST_N` asks for more rows before a task is judged. In the mixed simulation (mock models, seed 1) the night-8 candidate loses two of its three tasks this way and is rejected for coverage. Certified per-task bounds (FR-16.3) can replace the point estimates.
- The per-task alert uses the Wilson upper bound of audited precision, as the version-level alert does: on live traffic, action needs strong evidence. It looks after every tick ([ADR 0024](0024-evidence-foundations.md) has the numbers); the anytime-valid alert (FR-16.2) can take over both.

## Alternatives

- **A per-task gate on the 95% Wilson upper bound** (fail only when the bound is below the floor). It flaps less, but it reverses the burden of proof at admission: a task fails only on strong evidence that it is bad, so 9 of 10, 36 of 40 and 91 of 100 right all pass a 95% floor. A task sharing an adapter would ship at 90% where an adapter of its own at 94% is rejected, and once live, a 90% task with 20 audits has an upper bound near 97%, so the per-task alert would not fire either. Admission is where the burden of proof is on the candidate.
- **A golden set per task**, split by task before the even/odd split. Cleaner on paper, but it changes which rows calibrate the global threshold, so every existing number would move, including the single-task reference simulation.
- **Disable a task on the live version on a per-task alert.** Automatic action on live traffic is what the version-level alert avoids too; an operator pins the task instead, and the next version is checked afresh.
- **Make per-task thresholds opt-in.** It would keep the multi-task runs unchanged by default, but leave every shared adapter serving its hardest task below target by default. The opt-out (`RATCHET_PER_TASK_CALIBRATION=0`) keeps v0.4.0's behaviour reproducible instead.
