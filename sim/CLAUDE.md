# CLAUDE.md: `sim/` (offline simulation)

Mock models that let the whole loop run in seconds with no keys or GPUs. Used by `make sim`, the mock gateway (dashboard and Scout), `tests/test_system.py`, `tests/test_scout.py` and `tests/test_mock_world.py`.

- `tickets.py`: 20 synthetic support-ticket templates (6 categories, 4 priorities, "easy"/"hard"), plus 3 drift templates that appear from `drift_day` (a product launch). `REGISTRY` maps ticket text → ground truth so mock models can look it up. The vocabularies (`CATEGORIES`, `PRIORITIES`, and Scout's `SOURCE_TYPES` and `FACT_TYPES` in `ratchet/scout/prompts.py`) come from `ratchet/vocab.py`, the lists the built-in tasks check labels against (FR-2.14), kept as lists in the same order so the prompts and the mock student's draws do not move. Change a label there, never here; every answer the mock models write must stay valid under the built-in specs (`test_out_of_vocab_label_invalid`), or votes and examples drop and the reference simulation moves.
- `mock_models.py`:
  - `MockTeacher`: always right on labels, 2.4 s latency, bills 300 reasoning tokens. Also answers Scout's pinned planner and writer prompts (`_pinned_answer`).
  - `MockStudent`: skill per template = `max(0.35, ceil × (1 − e^(−n/6)))` with ceil 0.985 easy / 0.86 hard; exact texts it trained on are known. When it does not know a ticket, 15% of the time its samples agree on the **same wrong answer** with fairly high probability (the case audits and shadow exist for). Asked for logprobs (the router always asks), each sample also lists its tokens in `logprobs_content` (`_tokens`: `approx_tokens(text)` pieces of about 4 characters, the last taking the rest, each with the sample's constant logprob, and itself as its one alternative when the client sent `top_logprobs`), so they spell the text and `exp` of their mean is the sample's token probability (FR-1.14). No random draw is involved, so the simulation does not move. The mock teacher lists no tokens, so a teacher-served mock choice has `logprobs.content: null`.
  - Both honour `n` (the mock teacher returns `n` copies of its answer; the student `n` independent samples, so the first `RATCHET_SAMPLES` of a larger call are the samples a one-choice request gets), `stop` (the answer ends before the first stop string) and `max_tokens` (cut at about 4 characters per token, `finish_reason` `length`) from `params` (`_generate`). Ticket and research answers are short and contain no stop string, so the simulation does not move.
  - `MockFleet`: trainer + evaluator + resolver. The trainer finds each row's template as the student will see the request, from its messages and the stored conditions its allowlist passes (`row["params"]` through `GenParams.from_stored`, then `policy.student`, as `evaluate` and the router send it), so a row the demo did not write lands in the generic world instead of crashing Night School, and stored `tools` the student is not sent train the free-text template it is served. `corrupt_on_deploy` breaks the `fragile` slices (billing/refund/security tickets; `paper`/`docs` triage; `date` reads) for a version once it reaches canary/live (fault injection for rollback demos). `student_outage(seconds)` makes `resolve` return a `DownStudent` (every call raises `httpx.ConnectError`) for canary and live versions until the deadline on `MockFleet(clock=)`, for the circuit-breaker demo (`POST /ratchet/demo/student-outage`). Students name their endpoint in `base_url` (`PRODUCTION` for canary and live, `STAGING` for shadow and the golden eval), because the router keeps one breaker per endpoint and role; `MockStudent` is still built per call, so the sampling seeds are unchanged.
- `research.py`: the mock research world for Scout. 8 questions (facts from the original papers), each phrased 4 ways, with 72 simulated search results (12 templates × 6 variants) on `example.org`. Each template has fixed labels for `source-triage` and `page-read`. `REGISTRY` maps request text → `ResearchItem`; `search()` returns a deterministic sample per query; `ResearchStream` feeds the simulator (60% triage, 40% read; questions 7–8 only from `drift_day`). `plan_answer` / `write_answer` back the mock teacher's pinned answers.
- `world.py`: one `lookup(messages, params=None, strict=False)` over tickets, then research items, then the generic world, the `Item` protocol, and the workloads `tickets`, `research`, `mixed`, `schema`, `tools` (`make_stream`, `night_task`). It never raises for a request the gateway accepts. With `strict` (`RATCHET_MOCK_STRICT=1`, passed to `MockTeacher(strict=)` and `MockFleet(strict=)`) anything but a ticket or research text raises `KeyError`, including a request with no user message or with non-text content, and so does `MockTeacher` for a Scout writer request whose facts it cannot read; the mock gateway turns that into a 400. The trainer and the golden eval are never strict: they read rows already stored.
- `generic.py`: the generic world ([ADR 0041](../docs/adr/0041-generic-mock-world.md)), for every request the registries do not know. `item(messages, params, task)` picks a sub-world from what a model is sent: `tools` (function tools offered, `tool_choice` not `none`, the last message not a tool result: a call to the catalogue `TOOLS`, `lookup_order(order_id)` and `refund(order_id, amount, reason)`, with arguments read from the prompt by regex, a call to a client's own tool with arguments from its schema, or a plain reply when there is no order number; a forced `tool_choice` is honoured), `schema` (`response_format` json_schema: `instance_from_schema`, within a budget of `MAX_NODES` values and about `MAX_BYTES` of JSON, a copied enum or const charged by its size and an enum's first `MAX_ENUM` distinct values drawn, so a hostile schema on the public mock gateway costs milliseconds; a number's `multipleOf` passes a validator's quotient test; a `pattern` is not honoured), `json` (json_object: `{"answer": ...}`) and `text` (`[mock teacher] ` and a restatement; `final` after a tool result restates the result). `GenericItem` has the `Item` interface plus `world`, `calls(labels, salt)` (the tool calls, or None) and `data` (what it renders from). Its labels: the enum, boolean and number fields of a schema instance (enums first, so a slip or a confidently wrong answer changes an enum), the tool and refund reason of a call, the framing (`focus`) of a free-text answer. `fragile`: refund calls, schema answers whose first enum takes its first value, free text framed as steps. Difficulty: `hard` for tools and for schemas with more than three labels. `SchemaStream` (three schemas, a nested fourth from `drift_day`) and `ToolStream` (look-ups, refunds, questions no tool answers) are the `schema` and `tools` workloads; their prompts hold no personal data (short order numbers and amounts only), so redaction never changes them.
- The mock models fill `Completion.tool_calls` for a generic tool call (no content, finish `tool_calls`). The real provider does not read tool calls yet and the router refuses a teacher answer that ends in one (502 `tool_calls_unsupported`), so by default (`tools` forwarded to neither model) the tools workload is answered and learned as free text.
- `simulate.py`: CLI (`--days --requests --drift-day --bad-deploy-version --workload --seed`) and `run(args)` for tests. After each night it records the day's simulated compute (`ratchet.cost.record_simulated_day`: the endpoint up `RATCHET_MOCK_ENDPOINT_HOURS` from the start of the day and a training job of 600 s + 0.05 s per example from 22:00, on the synthetic clock), and the result's `cost` is the cost report; the table prints its GPU-hour line, labelled simulation. Recording writes compute intervals only, so no pinned number moves.

### Generic item interface

The mock models only see this interface (`sim/world.py` `Item`), so tickets and research calls share one skill model:

`text`, `template`, `difficulty` (`easy`/`hard`), `task`, `params` (the `GenParams` it is sent with: a schema or tools; None for tickets and research), `labels` (right answer), `label_space` (possible values per label, each with at least one value besides the right one), `fragile` (broken by a corrupted deploy), `answer(labels)` (JSON text), `messages()`.

To add a workload, implement these on its item class, register its texts so `world.lookup` finds them (or build its items with `generic.item`, which needs no registry), and add it to `make_stream` and `WORKLOADS` (and `gateway.WORKLOADS`).

Rules:

- These parameters are assumptions, not measurements. Never present simulation output as real model quality.
- If you change mock parameters, re-run `make sim` (and `--workload research`, `--workload mixed`) with seeds 1, 2, 3, 7, 11 and update [docs/TESTING.md](../docs/TESTING.md) if the trend changes.
- `make sim` (seed 7, 10 days × 2,000, drift day 5, corrupted v3) is pinned exactly by `tests/fixtures/sim_reference_seed7.json` and `test_reference_simulation_unchanged`. Any change to the mock models, the streams or the loop that moves it fails that test. If the move is intended, run `python scripts/regen_sim_reference.py` and add a CHANGELOG line that says why ([tests/CLAUDE.md](../tests/CLAUDE.md#the-reference-simulation-fixture)).
- Keep it deterministic: all randomness goes through seeded `random.Random` or `_rng(...)`.
- **The generic world draws nothing from a stream.** Its labels come from sha256 of the request's text (`generic._seed`), each schema instance from its own `random.Random` seeded that way, so the same request gets the same answer in the gateway, the simulator, the trainer and the golden eval, and no ticket or research draw moves. Its templates are keyed by what a model is sent (the schema name, the sorted tool names, a digest of the system prompt), never by the task name, which no model sees. Generic paths are reached only for texts outside the registries; keep it that way, or `make sim` and the reference fixtures move.
- **Do not change the order of random draws for tickets.** `TicketStream.sample`, the key order of `Ticket.label_space` (`category`, then `priority`) and the draw order in `MockStudent.complete` decide every ticket number. With them unchanged, `make sim` still reproduces the v0.1 table in README and TESTING exactly. Give new workloads their own RNG (as `ResearchStream` and `MixedStream` do) instead of drawing from the ticket stream's.
- Scout messages in `research.py` must be built with `ratchet/scout/prompts.py`, never by hand, or mock lookups break.
